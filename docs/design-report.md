## 1. スコープ設計 — 何を作り、何を作らないか

### 1.1 想定タイムライン（この構造に固定する）

```
┌──────────────────────────────────────────────────────┐
│ テロップ層     [T1] [T2]  [T3]      [T4] [T5]        │ ← ②。重なりは上下に自動配置
├──────────────────────────────────────────────────────┤
│ ビデオ         ████████████████████████████████████   │ ← ①。単一素材をカットで分割した区間の連結
│  ＋画角          [Z1]    [SW1]      [Z2]              │ ← ③。ズーム＋話者切替。ビデオ区間の属性
├──────────────────────────────────────────────────────┤
│ BGM            ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   │ ← 1本のみ。音量とフェードだけ
└──────────────────────────────────────────────────────┘
```

トラック数は可変にしません。**この4層固定**が、実装量を汎用NLEの1/5に抑える鍵です。

## 2. ①②③ の実現可能性

### 2.1 ① カット編集・テンポ調整

| サブ機能 | 実現度 | 手法 | 難所 |
|---|---|---|---|
| 無音カット | ◎ 95% | Silero VAD v6 + ffmpeg `silencedetect` の二重判定 | 閾値が好みに直結 → §12の学習対象 |
| フィラー除去 | ◯ 85% | 既存 `fillers.py`（表記ゆれ正規化済み） | 「まあ」「なんか」は意味を持つ場合がある |
| テンポ調整 | ◯ 80% | 語間ポーズの圧縮（0.5秒超 → 0.15秒） | 間を潰しすぎると笑いどころが死ぬ |
| 言い直し検出 | △ 60〜70% | n-gram重複 + LLM判定 | **最大の難所** |

**言い直し検出の内訳**（正直に）:
- 「これはあの、これはですね」→ 表層n-gram重複で検出可能（易）
- 「今日は3つ紹介します。あ、4つでした」→ 意味的自己訂正。**LLMでないと無理**（中）
- 「〜なんですけど、まあそれは置いといて」→ 切るか残すかは**編集者の好み**（ほぼ不可能）

現実解: 表層重複はルールで確実に取る。意味的訂正はLLMに候補を出させ、**確信度を付けてレビューUIのグレーゾーンに回す**。全自動にしない。

### 2.2 ② 自動文字起こし・テロップ — 精度の現実

2026年2月の日本語自然会話ASRベンチマーク（RTX 5090、20クリップ580秒、[出典](https://neosophie.com/en/blog/20260226-japanese-asr-benchmark)）:

| モデル | WER | CER | RTF | 備考 |
|---|---|---|---|---|
| **qwen3-asr-1.7b** | **0.185** | **0.140** | 0.036 | **最高精度**。句読点も自然 |
| **whisper-large-v3-turbo** | 0.218 | 0.184 | **0.013** | 文脈理解が最強。弱点は**ハルシネーション** |
| parakeet-tdt-0.6b-v3 | 0.344 | 0.321 | 0.003 | 爆速だが低精度 |
| reazonspeech-nemo-v2 | 0.348 | 0.329 | 0.020 | 放送メディア語彙に強い |
| **kotoba-whisper-v2.0** | 0.534 | 0.495 | 0.008 | **自然会話では実用外**。反復ループ、フィラー直後の語落ち |

**「誤字脱字の修正作業をほぼゼロ」は、単一モデルの精度向上だけでは達成できません。** 素の CER 14〜18% は「1テロップ（8〜16文字）につき1〜2回、修正箇所が出る」体感です。

**24GBのおかげで、精度を積み上げる手が全部打てます**（§9.2で詳述）:

| 手 | 効果（CERの相対改善） | メモリコスト |
|---|---|---|
| 1. **2パス構成**（turbo → 低信頼度だけ large-v3 で再認識） | −10〜15% | +4.5GB |
| 2. `hotwords` に固有名詞辞書（**操作ログから自動生成**・§12.3.3） | −8〜15% | ほぼゼロ |
| 3. LLM後処理（同音異義語の文脈補正） | −5〜10% | +6GB（Ollama）or API |
| 4. 置換辞書（**同じ誤変換が3回出たら自動登録**） | 使うほど効く | ほぼゼロ |
| **積み上げ後の着地見込み** | **CER 0.184 → 0.11〜0.14** | 合計 約13GB（24GBに収まる） |

> **設計判断**: それでも CER はゼロにならないので、**「修正1箇所あたり30秒 → 3秒」を目標にします**。§3のレビュー速度の考え方をテロップ修正にもそのまま適用します。

### 2.3 ③ ズーム・画角

| サブ機能 | 実現度 | 手法 |
|---|---|---|
| 人物検出・追跡 | ◎ 90% | MediaPipe Face Detection / FaceLandmarker（Apache-2.0） |
| **話者アクティブ判定（複数人）** | ◯ 70〜80% | **口唇開閉量 × 音声RMS の時系列相関**（§7.2） |
| 9:16 オートリフレーム（横素材） | ◯ 80% | 顔中心のクロップ枠を時系列平滑化 |
| 「強調箇所で人物アップ」 | ◯ 75% | 韻律z-score + テキスト分類 → ズームキーフレーム |
| **「視聴者が飽きそうな箇所」** | ✗ **不可能** | 下記 |

**不可能な理由**: 本当に推定するには**視聴維持率データ（YouTube Analytics の離脱グラフ）**が要ります。動画単体の信号からは推定できません。LLMに聞けば答えは返りますが、**根拠のないもっともらしい嘘**です。

**代替（③の要件を満たす実装）**: 「飽き」の推定をやめ、**「変化の欠如」という代理指標でUI上に注意マークを出す**。ズームは自動で入れません。

```
if 同一画角が継続 > style.max_static_shot_sec (例 4.5秒):
    → タイムライン上に「⚠ 画が動いていません（4.8秒）」マーカーを表示
    → クリックで「ここにズームを追加」ボタンが出る（適用は人間が決める）
```

**AIが判断を放棄していることが明示される**ので、誤った自動処理より信頼できます。

## 3. 【最重要の設計軸】レビュー速度

### 3.1 「精度より確認の速さ」は正しい

```
確認コスト = 「人間が確認する候補数」 × 「1件あたりの確認時間」
```

候補100件・精度90%（10件が誤り）でも、人間は「どの10件が誤りか」を知らないので**全100件を確認せざるを得ません**。精度を95%に上げても確認件数は100件のまま。**確認コストは減りません。**

**ただし精度は間接的に効きます**。精度が上がる＝**確信度の分離が良くなる**ので、「0.90以上は無条件に信じてよい」範囲が広がり、**確認件数そのものが減る**からです。

> **精度改善の努力は「正解率を上げる」ではなく「確信度のキャリブレーションを良くする」に向けるべきです。**

### 3.2 目標値

| | 現状 | 目標 |
|---|---|---|
| 1本あたりのカット作業 | **30〜60分** | **2〜3分**（解析待ちを除く） |
| カット候補の件数（20分素材） | — | 約110〜130件 |
| **人間が実際に見る件数** | 全件 | **25件前後** |
| **1件あたりの判断時間** | — | **2〜2.5秒** |

### 3.3 レビューUI設計

#### 3.3.1 確信度による3分割（件数を減らす主装置）

| 確信度 | 扱い | 20分素材での想定件数 |
|---|---|---|
| **`conf >= 0.90`** | **デフォルトで承認済み**。「高確信度 71件を自動承認しました ▸確認する」 | 71件（60%） |
| **`0.60 <= conf < 0.90`** | **レビュー対象**。1件ずつ確認 | **35件（30%）** |
| **`conf < 0.60`** | **デフォルトで却下**。「他に12件 ▸見る」 | 12件（10%） |

**+ タイプ別の一括処理**: フィラー除去（「えー」「あの」等）は個別確認不要。**一覧で42件をまとめて表示し、チェックボックスで例外だけ外す**（15秒）。

→ **118件 → 実際に1件ずつ見るのは25件程度**

#### 3.3.2 「カットレビューモード」（全画面・キーボード中心）

```
┌────────────────────────────────────────────────────────────────┐
│  カット候補  12 / 25   ✅承認 8   ❌却下 3   ⏸保留 1            │
├────────────────────────────────────────────────────────────────┤
│              ┌──────────────────────┐                           │
│              │   プレビュー          │  ← 自動ループ再生中        │
│              │   (ProRes Proxy)     │    「前0.5秒→(カット)→後0.5秒」│
│              └──────────────────────┘                           │
│  波形:  ▁▃▅█▇▅▃▁▁········▁▁▃▅█▇▅                                │
│         └── 残す 0.5s ──┘│ 0.82秒 │└── 残す 0.5s ──┘            │
│  文脈:  「…めちゃくちゃ使えるんですよ」 ⟨0.82秒⟩ 「それで、次に…」│
│  種別: 無音   確信度: ████████░░ 0.82                           │
├────────────────────────────────────────────────────────────────┤
│  [Y]承認→次へ  [N]却下→次へ  [Space]再生/停止                   │
│  [←→]境界±1F  [Shift+←→]±5F  [S]保留  [U]取り消し  [Enter]一括承認│
└────────────────────────────────────────────────────────────────┘
```

#### 3.3.3 速度を決める7つの設計

| # | 設計 | 効果 |
|---|---|---|
| 1 | **ループ再生の自動開始** — 候補に移った瞬間に自動再生 | −1.5秒/件 |
| 2 | **🔴 カット適用後の音を聞かせる** — 判断すべきは「繋ぎが自然か」であって「そこが無音か」ではない | **判断そのものが速くなる。最重要** |
| 3 | **Y/N の2キーで完結し自動で次へ** — マウスを一切使わせない | −1〜2秒/件 |
| 4 | **確信度グループ化**（§3.3.1） | **件数が118→25に** |
| 5 | **🔴 ProRes Proxy の短尺クリップ**（§8.5） — 全フレームIフレーム＋HWデコードで**ループの継ぎ目が瞬時** | **体感の"サクサク感"を決める** |
| 6 | **境界微調整も同じキーボード** — `←→` で±1フレーム、即座にループ再生が更新 | 微調整 15秒→5秒 |
| 7 | **`U` でいつでも1つ戻れる** | 心理的効果（判断が速くなる） |

#### 3.3.4 「通し確認モード」（併設）

### 4.2 Electron を採る決定的な理由

**Mac実機が入手不可（§10）という制約下では、「描画が完全に同一」であることの価値が跳ね上がります。**

- Tauri は Mac が WKWebView になり、**開発中は一切問題が出ず友達のMacでだけ壊れる**。開発者は再現すらできない
- Electron は Chromium 統一なので、**UI・レビューUI・タイムライン・Canvasテロップ描画は Windows で検証すれば Mac でも同じ結果になる**
- これが §10.2 の「Windows先行開発戦略」を成立させる前提条件です

副次的な理由: ①テロップWYSIWYG（核心的難所）が Canvas だと圧倒的に楽、②§3のレビューUIは応答性と細かい演出が命でWebのほうが作りやすい、③MITでライセンスがクリーン（収益化前提では重要）。

### 4.3 【検討の記録】PySide6 案（不採用）

| ライセンス | MIT | ⚠️ LGPL-3.0（PyInstallerで固めると条件充足が判断困難）**←収益化前提では致命的** |

## 5. プレビュー再生アーキテクチャ

### 5.1 HTML5 `<video>` の限界

編集後のタイムラインは「元素材の複数区間を連結したもの」です（[出典](https://web.dev/articles/requestvideoframecallback-rvfc) / [W3C issue](https://github.com/w3c/media-and-entertainment/issues/4)）:

- **フレーム精度のシークは保証されない**
- `requestVideoFrameCallback` で実表示フレーム時刻は取れるが**ベストエフォート**
- 区間境界で `currentTime` をジャンプさせると**毎回シーク遅延（数十〜数百ms）**

### 5.2 推奨: 案A（プロキシ事前生成）を基本、編集中は案Bを併用

| 案 | 方式 | フレーム精度 | 実装コスト | 反映の遅さ |
|---|---|---|---|---|
| **A** | **カット済みプロキシを事前生成し単一 `<video>` で再生** | ◎ | **小（3〜5人日）** | ✗ カット変更のたびに再生成 |
| B | 元素材を1本の `<video>` で再生し境界で `currentTime` ジャンプ | ✗ 境界でカクつく | 中（8〜12人日） | ◎ 即時 |
| C | WebCodecs でフレーム単位デコード → Canvas に自前描画 | ◎ | **特大（25〜40人日）** | ◎ 即時 |

1. **プレビュープロキシ**: 540×960（縦）/ 960×540（横）H.264 `-g 15`
2. **編集中は案Bで即時プレビュー**、**レビュー開始時に案Aでプロキシ再生成**
3. **🔴 §3のレビューUIには専用の短尺クリップ**（§8.5）。約1.2秒を**ProRes Proxy**で25本。生成は10〜20秒

案Cは作りません（単体で1〜2ヶ月）。

### 5.3 フレーム精度が必要な箇所

| 場面 | フレーム精度 | 実現方法 |
|---|---|---|
| 通常再生・ループ再生 | ✗ 不要 | `<video>` に任せる |
| **カット点の微調整（コマ送り）** | ✅ **必要** | **静止画で解決**: 前後±10フレームを ffmpeg で PNG に切り出し、コマ送りはPNG切り替え |
| テロップのタイミング調整 | △ ±1フレームで十分 | 同上 |
| 波形上での位置指定 | ✅ 必要 | 波形は独自描画なのでサンプル単位で正確 |

**「コマ送りをPNGでやる」** のが肝です。プレイヤーのフレーム精度問題をUIの都合で回避できます。

## 6. テロップのレンダリング — 案C で確定

### 6.1 参考画像から読み取った現要件

友達の実際のテロップの特徴:
- **白の太ゴシック体 + 黒の太い縁取り（袋文字）**、影・グラデーションなし
- **画面上部中央**に配置、2行程度で折り返し、文字サイズは画面幅の大部分
- **文節の途中で改行**されている（「お前顔映ってもい／いな」）← §6.6 で解決する課題

### 6.2 `ffmpeg drawtext` を不採用にする理由

- 縁取り（`borderw`）は**1本のみ**、色も1色。二重縁取り不可
- グラデーション塗り不可／影は1つだけ・ぼかし不可／背景ボックスは矩形のみ
- 日本語フォントのフォールバック制御が効かない
- **テキストのエスケープが地獄**（`:` `'` `%` `\` すべて特殊文字）

### 6.3 【確定】案C（Canvas → PNG → overlay）

| 案 | 方式 | WYSIWYG一致 | 表現力 | 書き出しコスト | 実装 |
|---|---|---|---|---|---|
| A | ffmpeg `drawtext` | ✗ | ✗ | ◎ | 小 |
| B | ASS字幕 + libass | ◎ 同一エンジン | ◯ **現要件は満たすがグラデ不可** | ◎ | 中 |
| **C（確定）** | **Canvas → 透過PNG → ffmpeg `overlay`** | ◎ **同一コード** | ◎ **Canvasの全表現力** | ◯ | 中 |

**現要件（白ゴシック＋黒袋文字）だけなら案Bでも表現でき、1〜2人日短縮できます。しかし「後から装飾を追加できる仕様であること」という条件があるため、案Cを採ります。** この短縮は取りません。

**案Cを採る具体的な利点**:
1. **一致が構造的保証**。プレビューと書き出しが同じCanvasコード
2. **後から追加できる装飾**: グラデーション塗り、二重縁取り（`strokeText` の多重描画）、角丸背景、letter-spacing、テロップアニメーション（ポップイン等）。**すべてスタイル定義の追加だけで実現でき、レンダラの改修が不要**
3. Phase4 の「スタイルのカスタマイズUI」に自然に発展する
4. ffmpeg 側は `overlay` 1つ。`drawtext` が要求する libfreetype/libharfbuzz/fontconfig が不要

**拡張性を担保する設計**: スタイル定義をCSSライクなスキーマにし、レンダラは「定義を解釈して描く」だけにします。新しい装飾を足すときは**スキーマにフィールドを1つ追加してレンダラに1分岐足す**だけ。

```yaml

  font: "Zen Kaku Gothic New"
  weight: 900
  size_px: 96
  color: "#FFFFFF"
  stroke: { color: "#000000", width_px: 10 }
  align: "center"
  y_pct: 14                    # 画面上部（参考画像に合わせる）
```

### 6.4 実装設計（性能が肝）

素朴に「全フレームをPNG化」すると20分×30fps = 36,000枚で破綻します。**テロップは大半が静止画**という性質を使います。

**レイアウト変化点でセグメント化**:
```
表示中のテロップ:  {}   {T1}    {T1,T2}   {T2}   {}    {T3}   {}
セグメント:        S0 │  S1   │   S2    │  S3  │ S4 │  S5  │ S6
PNG:              なし  1枚      1枚      1枚   なし   1枚   なし
```

- PNG枚数 ≒ テロップ数 × 1〜2。20分素材で200テロップなら **200〜400枚**
- 1080×1920 の透過PNGは文字部分だけなので圧縮後 50〜300KB → 合計 **20〜100MB**
- **Canvas → PNG の生成時間**: 20〜60ms/枚。400枚で **8〜24秒**

**overlay の適用方法 — M2 Air ではここがCPUボトルネック**:

| 方式 | CPU負荷 | ディスク | 判定 |
|---|---|---|---|
| **(a) `overlay` を N段チェーン**（`enable='between(t,a,b)'`） | 段数に比例して増える可能性 | 100MB | **第一選択。Phase 0 で実測** |
| (b) PNG群を `concat` → アルファ付き中間動画（QTRLE）→ `overlay` 1回 | 低い | **3〜10GB** ⚠️ | §9.4の容量目標を超える |
| (c) ProRes 4444 | 最低 | **30GB超** ❌ | 不採用 |
| (d) VP9 alpha (yuva420p/WebM) | 高い（libvpxはソフトウェア） | 200〜800MB | CPU負荷が本末転倒 |

> **🔴 Phase 0 で「overlay 200段の実行速度をM2 Airで実測」します（§16）。** 実効150fps以上なら (a) で確定。遅ければ (b) にフォールバックしますが、**§9.4のSSD目標を超えるので、その場合は時間分割方式を検討します**。

### 6.5 落とし穴

|---|---|
| **フォントが読み込まれる前に描画** | `document.fonts.ready` を待つ。**Webフォントをアプリに同梱** |

### 6.6 【新規要件】文節単位の自動改行 — BudouX を採用

**課題**: 参考画像の「お前顔映ってもい／いな」のように、単純な文字数折り返しは文節の途中で切れて読みにくくなります。既存 `autotelop/telop.py` の `_wrap()` は文字数ベース + 簡易禁則のみで、この問題を解決できません。

**解決策: [BudouX](https://github.com/google/budoux)（Google製）を使う。**

| 特徴 | 内容 |
|---|---|
| 目的 | **日本語の自然な改行位置（文節境界）を機械学習で推定する専用ライブラリ** |
| サイズ | **約20KB（MLモデル込み）**。外部API・辞書不要 |
| 対応言語 | 日本語・中国語（簡体/繁体） |
| **バインディング** | **JavaScript / Python / Java の公式サポート** |
| 実績 | **ICU に採用**。Android 14+、Chrome 119+ の `word-break: auto-phrase` の実装。adobe.com 等で使用 |
| ライセンス | Apache-2.0（Google OSS。**Phase 0 で最終確認**） |

**採用の決め手**: **JavaScript版があるので、Canvas描画側（TypeScript）でそのまま使えます。** Python側とTypeScript側で二重実装する必要がなく、**プレビューと書き出しで改行位置が一致することが構造的に保証されます**（§6.3の設計思想と同じ）。SudachiPy や GiNZA だと Python 側にしかなく、Canvas 側に持ち込めません。

**アルゴリズム**:
```typescript
function wrapTelop(text: string, maxCharsPerLine: number, maxLines: number): string[] {
  // 1. BudouX で文節（phrase）に分割
  const phrases = budouxParser.parse(text);   // ["お前", "顔", "映っても", "いいな"]

  // 2. 文節を貪欲に詰めて行を作る
  const lines: string[] = [];
  let cur = "";
  for (const p of phrases) {
    if (cur.length + p.length <= maxCharsPerLine) { cur += p; }
    else {
      if (cur) lines.push(cur);
      // 3. 1文節が1行に収まらない場合のみ、文字数で強制分割（禁則処理を適用）
      cur = p.length > maxCharsPerLine ? forceSplitWithKinsoku(p, maxCharsPerLine, lines) : p;
    }
  }
  if (cur) lines.push(cur);

  // 4. maxLines を超えたら、テロップ自体を時間分割する（詰め込まない）
  return lines;
}
```

**既存 `telop._wrap()` からの変更点**:
- 禁則処理（`_NO_LINE_START`）は**残す**（文節分割後も、句読点が行頭に来るケースはある）
- **`maxLines` 超過時の扱いを変更**: 既存実装は「溢れは最終行に詰める」ですが、**テロップを時間分割して2つに分ける**ほうが読みやすい。文節境界で分けられるので自然に分割できます

**工数**: **1.5人日**（BudouX統合 0.5 + 折り返しロジック 0.5 + 既存禁則との統合とテスト 0.5）。Phase2 に含めます。

## 7. 【新規】縦横両対応と複数人対応

### 7.1 縦横両対応の設計

**入力（4パターン）× 出力（3プリセット）** の組み合わせを、`reframe_mode` という1つの属性に集約します。

| 入力 | 出力 | `reframe_mode` | 処理 |
|---|---|---|---|
| **縦（9:16）** | 縦（1080×1920） | `none` | **クロップ不要**。ズームのみ。顔追従は「ズームの中心決め」にのみ使う |
| **横（16:9）** | 縦（1080×1920） | `crop_9_16` | **9:16クロップ + 顔追従パン**。横幅の31.6%しか使えない（下記） |
| **横（16:9）** | 横（1920×1080） | `none` | クロップ不要。ズームのみ |
| **縦（9:16）** | 横（1920×1080） | `pad` | 横幅が足りない → **左右に余白（背景ぼかし or 単色）**。非推奨だが対応 |
| 正方形・その他 | いずれか | `fit` / `crop_generic` | 汎用パス |

**書き出しプリセット（3つ）**:
- **縦 1080×1920**（ショート / Reels / TikTok）← 既定
- **横 1920×1080**（YouTube 通常）
- **正方形 1080×1080**

**入力の向きは読み込み時に自動判定**し、出力プリセットとの組み合わせから `reframe_mode` を決めます。友達に「縦ですか横ですか」と聞かない設計です（IT知識なしのため）。

**横→縦クロップの物理的限界**（正直に）:
```
素材 1920×1080 → 縦枠 1080×1920 に fill
スケール係数 = 1920/1080 = 1.7778
スケール後の素材幅 = 3413px、表示される幅 = 1080px
→ 元の横幅のうち 1080/3413 = 31.6% しか残らない（約68%を捨てる）
パン可能範囲 = ±(3413 − 1080)/2 = ±1166px
```

**複数人が画面の左右端にいる横素材を9:16にするのは原理的に不可能**です。設定で選ばせます:
- **(a) 話者だけを追う**（もう一人は映らない）← 既定。テンポが良く、ショート向き
- **(b) 全員が収まるよう縮小し、上下に余白**（背景ぼかし）← 会話の空気を残したい場合

### 7.2 【新規】話者アクティブ判定（複数人対応）

**ライセンスがクリーンな実装を自作します。** Light-ASD / TalkNet-ASD は研究コードで商用条項が不明瞭、Ultralytics YOLO は AGPL-3.0 のため使いません（§13.1）。

**アルゴリズム: 口唇開閉量 × 音声RMS の時系列相関**

```
1. MediaPipe FaceLandmarker で全顔トラックのランドマークを取得（360pプロキシ、5fps）
2. 各トラックについて「口の開き具合」を計算:
     mouth_open = |上唇内側(13) − 下唇内側(14)| / 顔幅(左右目尻間距離)
   ※顔幅で正規化することで、顔の大きさ（カメラからの距離）に依存しなくなる
3. 音声RMSを同じ時間分解能（5Hz）にリサンプル
4. 窓幅 1.0秒・ホップ 0.2秒 のスライディング窓で、各トラックの
   mouth_open 系列と RMS 系列の Pearson 相関係数を計算
5. 各窓で相関が最大かつ閾値（既定 0.35）を超えるトラックを「その窓の話者」とする
6. 全トラックが閾値未満 → 「話者不明」
   2トラック以上が閾値超 → 「同時発話」
7. メディアンフィルタ（窓5）で時系列を平滑化し、瞬間的な誤判定を除去
8. 発話セグメント（ASRのセグメント）と突き合わせ、
   セグメント全体で最頻の話者IDを `segment.speaker_id` に確定
```

**精度の率直な見込み: 70〜80%**。研究レベルのASD（TalkNet等で85〜93%）には届きませんが、以下の理由で実用範囲です:
- **誤判定のコストが低い**: 画角が一瞬ずれるだけで、内容は失われない
- **§3のレビューUIで人間が直せる**（話者切り替えも承認/却下の対象にする）
- **保守的なルール（§7.3）で誤判定の影響を吸収する**（最小保持時間、掛け合い検出）

**うまくいかないケース（正直に）**:
| ケース | 挙動 | 対策 |
|---|---|---|
| 顔が横向き / 後ろ向き | 口唇ランドマークが取れない | そのトラックは「不明」→ 引きの画角 |
| マスク・手で口を覆う | 同上 | 同上 |
| 相槌・笑い声 | 短い発話は窓に埋もれる | §7.3の最小保持時間で吸収 |
| BGMや環境音が大きい | RMSが話者と無相関になる | 発話区間（VAD）内でのみ相関を計算する |
| 3人以上 | 精度が落ちる | 2人を主対象とする。3人以上は「引き」の頻度を上げる |

**工数: 6.5人日**（ランドマーク取得と正規化 1.5 / 相関計算と平滑化 2 / セグメント突き合わせ 1 / テストとチューニング 2）

### 7.3 【新規】話者切り替えのカメラワーク設計方針

**最も重要なのは「切り替えすぎないこと」です。** 相槌のたびに画が飛ぶのが、この種の自動編集で最も不自然に見える失敗です。

| # | ルール | 既定値 | 目的 |
|---|---|---|---|
| 1 | **最小保持時間** | `min_shot_sec: 1.5` | これ未満の話者交代では画角を変えない。**相槌で画が飛ぶのを防ぐ最重要ルール** |
| 2 | **切り替えクールダウン** | `switch_cooldown_sec: 2.0` | 直前の切り替えからこの時間は次の切り替えを抑制 |
| 3 | **🔴 掛け合い検出 → 引きに固定** | `pingpong_window_sec: 3.0` / `pingpong_count: 2` | **3秒以内に話者交代が2回以上起きたら、その区間全体を「引き」に固定する**。ピンポン切り替えを防ぐ |
| 4 | **同時発話 → 引き** | — | 2トラック以上が閾値超なら全員が収まる画角 |
| 5 | **話者不明・無音 → 直前の画角を維持** | — | 画が勝手に動かない |
| 6 | **切り替えは原則ハードカット** | `transition_via_wide: false` | 引きを経由すると遅い。ショートはテンポ優先 |
| 7 | **1分あたりの切り替え上限** | `max_switch_per_minute: 8` | 超過分は確信度の低い順に却下 |
| 8 | **文の途中では切り替えない** | — | ASRセグメント境界にスナップする |

**「引き」の定義**（`reframe_mode` 別）:
- `crop_9_16`: 検出されている全顔を含む**最小の9:16枠**。収まらなければ §7.1 の (a)/(b) 設定に従う
- `none`（縦素材 / 横→横）: `scale = 1.0`（クロップなしの全画面）

**ズーム（強調）との優先順位**: 話者切り替えとズームが同時に発生した場合、**話者切り替えを優先**します（誰が話しているか分からなくなるほうが致命的）。ズームは切り替え後 `zoom_cooldown_sec`（既定 1.0秒）を空けてから適用します。

**UIでの扱い**: 話者切り替えも**承認/却下の対象**にします（§3.3.7）。タイムライン上に切り替え点をマーカーで表示し、レビューモードで「切り替え適用後の映像」をループ再生して Y/N で判断できるようにします。

**工数: 2.5人日**（ルールエンジン 1.5 / UIとの接続 1）

### 7.4 単一話者の場合（縮退動作）

顔トラックが1つしか検出されない場合、§7.2/§7.3 は自動的に無効化され、従来通り「顔追従 + 強調ズーム」のみになります。**追加の分岐を書かず、話者数1の特殊ケースとして自然に縮退する**設計にします。

### 9.2 24GB を活かす精度設計 — 2パス構成

```
パス1: whisper.cpp large-v3-turbo で全体を高速に文字起こし（20分素材で2.9〜4.7分）
         ↓ 単語レベル信頼度が低いセグメント（conf < 0.6 ≒ 全体の15〜25%）を抽出
パス2: そのセグメントだけ large-v3 で再認識（4〜5分相当 → 1.7〜3.6分）
         ↓ 信頼度の高いほうを採用してマージ
パス3: hotwords（固有名詞辞書）+ LLM後処理で文脈補正
```

| 構成 | 20分素材の文字起こし | 実効CER見込み | メモリ |
|---|---|---|---|
| turbo 単独 | 2.9〜4.7分 | 0.184 | 2GB |
| large-v3 単独 | 8.7〜14.3分 | ~0.17 | 4.5GB |
| **2パス（推奨）** | **4.6〜8.3分** | **~0.16** | **6.5GB** |
| 2パス + hotwords + LLM後処理 | 5.3〜9.2分 | **0.11〜0.14** | 13GB |

**large-v3 単独と比べて、2パスは約半分の時間で同等以上の精度**になります。**これが24GBの最大の活用先**です。

> **補足**: ベンチマーク最高精度の **qwen3-asr-1.7b（CER 0.140）** も24GBなら transformers + MPS で載ります（約6GB）。ただしMac最適化が未知数なので、**Phase 0 で実測してから採否を決めます**（§16）。

#### 10.2.2 運用手順


#### 10.2.3 この戦略が効く理由

Electron を選んだことで、**Mac固有なのは「サイドカーの中身」と「ffmpegのエンコーダ」だけ**になりました。UIとレンダリング（＝開発工数の6割以上を占め、かつバグが出やすい領域）が完全に同一なので、**「Macでだけ見た目が崩れる」という最も追いにくいクラスの問題が構造的に発生しません**。

これは §4.2 で Electron を採用した理由そのものです。**基盤選定とMac非所持対策は同じ判断です。**

### 10.3 対策2: GitHub Actions macOSランナーを「CI」ではなく「検証環境」として使う

autotelop で **.app ビルドの実績**があります（無料の macOS ランナー、arm64）。これを**ビルドだけでなくテストと計測に拡張**します。

| やること | 内容 |
|---|---|
| **スモークテスト** | リポジトリに30秒のサンプル動画（縦1本・横1本・複数人1本）を入れ、毎PRで「解析が最後まで完走するか」をチェック |
| **golden file テスト** | `analysis.json` / `project.json` / **書き出しMP4の代表3フレームをPNG化したもの** を golden として保存し、差分を検出。**テロップWYSIWYGの回帰を自動で捕まえられる** |
| **🔴 スクリーンショット比較** | 同じテロップを Windows と macOSランナーの両方で Canvas 描画し、PNG差分を取る。**フォントラスタライズの差を自動検出**（§10.2.1 の🟡項目を自動化） |
| **性能回帰チェック** | 各工程の所要時間を記録し、前回比 ±20% を超えたら失敗させる |
| **ffmpeg ビルドの検証** | `ffmpeg -encoders` に `h264_videotoolbox` / `prores_videotoolbox` があり、`libx264` が**ない**ことを assert（§13.1の徹底） |
| **Python サイドカーの arm64 ビルド** | PyInstaller onedir を毎リリースでビルドし、成果物を配布 |

> ⚠️ **ランナーは Apple Silicon ですが、サーバ筐体でファンがあります。** M2 Air のファンレスとは冷却条件が違うので、**絶対値の性能見積もりには使えません**。**回帰検出（前回比）にのみ使う**と割り切ってください。

> 💡 **`tmate` アクションでランナーにSSH接続**できます。ヘッドレスなのでGUIデバッグはできませんが、**サイドカー単体・ffmpeg単体の対話的な検証には使えます**（whisper.cpp の CoreML 動作確認など）。これは有効な手段なので Phase 0 で確立します。

### 10.4 対策3: プラットフォーム差を4ファイルに閉じ込める

| 差異 | 閉じ込め先 |
|---|---|
| ASR バックエンド | `sidecar/asr/__init__.py` の `make_asr()` |
| エンコーダ/デコーダ | `sidecar/ffmpeg/platform_args.py` の `video_args()` |
| 顔検出 delegate | `sidecar/face/__init__.py` の `make_detector()` |

**この4ファイル以外に `if platform === 'darwin'` / `if sys.platform == "darwin"` を書かない**というルールを最初に決めます。**CIで grep して違反を検出**します（`rg "platform.*darwin" --glob '!{4ファイル}'` が空であることを assert）。

守れれば、**Macで壊れる範囲が予測可能**になります。

## 11. 決定論とLLMの責務分割 + IRスキーマ

### 11.1 分割原則

> **「時刻・座標・数値」は決定論。「意味・意図・感情」だけLLM。**
> **LLMには動画も音声も渡さない。IRのテキストと数値メトリクスだけ渡す。**

| 処理 | 対象 | 担当 | 使うもの |
|---|---|---|---|
| 音声抽出・CFR正規化・プロキシ生成 | ①②③ | 決定論 | ffmpeg (VideoToolbox / NVENC) |
| 発話区間検出(VAD) | ① | 決定論 | Silero VAD v6 |
| 文字起こし・単語タイムスタンプ | ①② | 決定論(ML) | whisper.cpp (CoreML) |
| 無音区間の抽出 | ① | 決定論 | VAD区間の補集合 + `silencedetect` |
| フィラー語検出 | ① | 決定論 | 既存 `fillers.py` |
| 表層的な言い直し検出 | ① | 決定論 | n-gram重複 + 時間近接 |
| **文節分割・改行位置決定** | ② | 決定論 | **BudouX（JS版）** |
| 韻律メトリクス（z-score） | ②③ | 決定論 | librosa / pyworld |
| シーンカット検出 | ③ | 決定論 | PySceneDetect |
| 顔検出・トラッキング | ③ | 決定論(ML) | MediaPipe (Metal delegate) |
| **話者アクティブ判定** | ③ | **決定論**（相関計算） | 口唇ランドマーク × RMS |
| **話者切り替えのカメラワーク** | ③ | **決定論**（ルールエンジン） | §7.3 |
| **意味的な言い直しの判定** | ① | **LLM** | IRのテキスト |
| **テロップスタイル分類** | ② | **LLM → Phase4でローカル分類器** | IRのテキスト + 韻律z-score |
| **誤字・同音異義語の文脈補正** | ② | **LLM** | IRのテキスト |
| **ズーム強調点の最終選択** | ③ | **LLM（候補は決定論が絞る）** | IRのテキスト + 韻律 |
| カット後タイムラインの再計算 | ①②③ | 決定論 | 既存 `cut.remap_point()` |
| レンダリング | ①②③ | 決定論 | Canvas + ffmpeg |

**「感情認識モデル」は使いません。** 日本語で商用可・高精度な音声感情認識OSSは2026年時点でも実質存在しません（SpeechBrain の IEMOCAP は英語、日本語モデルは演技音声由来で汎化が疑わしい）。代わりに **RMS/F0/話速の話者内z-score という連続量**で扱い、「怒り」ラベルは**テキスト側でLLM/分類器が判定**、z-scoreは補強証拠とします。

> 💡 **複数人対応で「話者内z-score」の意味が変わります。** 話者ごとに平均・分散が違うため、**`speaker_id` ごとに z-score を計算**します（§11.3）。これがないと、声の大きい人が常に「強調」判定されます。

> ⚠️ Praat（parselmouth）はGPLです。pyworld（修正BSD）を使ってください。

### 11.2 二重座標系の明示的分離（バグ防止の要）

| 接頭辞 | 意味 | 誰が持つ |
|---|---|---|
| `src_*` | **元素材のタイムコード**（カット前・素材ファイル先頭から） | `analysis.json` はこれのみ |
| `tl_*` | **編集後タイムライン座標**（カット適用後・シーケンス先頭から） | `remap_point()` を通した後だけ |

**規則**:
1. 解析パイプライン（`analysis.json`）は **`src_*` しか持たない**
2. `remap_point()` を通した瞬間に `tl_*` に改名する。**同じ変数に上書きしない**
3. **内部計算は秒(float)ではなく整数フレーム数で行う**（丸め誤差の累積を防ぐ）
4. UI表示は `tl_*`、書き出しコマンド生成は両方を使う

**①②③すべてに適用**します。テロップの表示時刻も、ズーム/話者切替のキーフレーム時刻も、カットの影響を受けるからです。

## 12. "自分風"を学習・再現させる方式

### 12.1 推奨: **(a') 機械可読プロファイル + (d) UI操作ログのフィードバックループ**

| (b) | 過去完成動画からのルール自動抽出 | 特大（15〜25人日） | ペア20本以上 | ◯ | △ | ゼロ |
| (c) | Few-shot例示 + LLMにタイムライン直接出力 | 中（5〜8人日） | 例20〜50件 | ◯ 意味は強い、時刻は✗ | △ | LLM毎回課金 |
| **(d)** | **UI操作ログのフィードバックループ** | **中（6〜9人日）** | **0（使いながら貯まる）** | **◎** | **◎ 操作履歴が可読** | **ゼロ** |
| (e) | 事例参照(RAG)／小規模分類器 | 中〜大 | ラベル100〜300件 | ◯ | ◯ | ゼロ |

**(a) CLAUDE.md方式を推さない理由**:
1. **非決定性** — 同じ入力で結果が揺れ、原因を切り分けられない。コード生成でCLAUDE.mdが機能するのはテストという検証器があるからで、動画編集にはない
2. **暗黙知は言語化できない** — 「間を詰める」と書いても 0.35秒なのか 0.68秒なのかは決まらない。"自分風"の実体は言語化されない数値
3. トークンコストが毎回かかる
4. フィードバックが構造化されず、矛盾した指示が堆積する

**(b) を推さない理由**: (d) が同じ価値を、初期データゼロ・実装コスト1/3で提供するため。

**自作アプリ化により (d) の価値が決定的に上がりました**: アプリ内の操作がそのままログになるので、**友達は何もしなくてよい**。回収できるのは「最終結果」ではなく「操作そのもの」（却下か微調整か、どれくらい動かしたか）で、特徴量との紐付けも確実、遅延ゼロです。

### 12.2 【検証】まず「カットのテンポ」だけで回るか → **回る**

| 理由 | 内容 |
|---|---|
| **パラメータ数が少ない** | `silence_cut_threshold_sec` / `silence_keep_margin_sec` / `fillers.context_exceptions` / `repeat.auto_apply_min_confidence` の**実質4個** |
| **1本あたりのサンプル数が多い** | 20分素材で**カット候補118件**。1本で有意な統計が取れる |
| **教師信号が明確** | 「承認/却下」は二値 |
| **特徴量が単純** | `silence_dur`（無音長）1変数でほぼ説明できる |
| **効果が体感しやすい** | 閾値が0.05秒変わるだけで候補数が10〜20件変わる |

**最小サンプル**: 却下率20%を検出するのに必要なサンプル数は二項検定で **30〜50件**。**1本のレビューで118件のログが取れる**ので、**1〜3本で最初の更新提案が出せます。**

→ **Phase1（カットのみ）の時点で学習ループが回り始めます。** 友達は「使うほど自分好みになる」体験を最初のリリースから得られます。

| 精度（4クラス） | 70〜85% | 80%前後（200件で） |
| 速度（20分素材・M2 Air） | **43〜55秒** | **1秒未満** |
| メモリ | 5.5〜6.5 GB | 0.5 GB |

**→ 使い込むほど速く・軽く・自分好みになります。** §8の処理時間もさらに短縮されます。

## 13. ライセンス — 収益化前提の確定方針

### 13.1 🔴【確定】最初から避けるものリスト

**収益化を検討する以上、以下は「後で差し替える」ではなく「最初から使わない」を設計上の制約とします。**

| 避けるもの | ライセンス | 何が起きるか | **代替（これを使う）** |
|---|---|---|---|
| 🔴 **libx264 / libx265** | **GPL** | **同梱するとアプリ全体がGPL** → ソース公開義務 | **VideoToolbox（Mac）/ NVENC（Win）/ OpenH264（フォールバック）** |
| 🔴 **Ultralytics YOLO**（v5以降/v8/v11/YOLO26） | **AGPL-3.0** | **クローズド商用不可**。ソース全公開かエンタープライズ購入 | **MediaPipe（Apache-2.0）** |
| 🔴 **libfdk-aac** | nonfree | 再配布不可 | 標準の `aac` エンコーダ |
| 🔴 **Praat / parselmouth** | **GPL** | 同上 | **pyworld（修正BSD）** |
| 🔴 **商用フォント**（モリサワ/フォントワークス等） | 商用 | 同梱に別途の埋め込み契約が必要 | **SIL OFL フォント**（§6.7） |
| 🔴 **再配布禁止のフリーフォント** | 個別規約 | 「商用利用可」でも**同梱は不可**なものが多い | 同上 |
| 🟠 **PySide6** | LGPL-3.0 | PyInstallerで固めると条件充足が判断困難 | **Electron（MIT）**（§4.3で不採用済） |
| 🟠 **Light-ASD / TalkNet-ASD** | 不明瞭（研究コード） | 商用条項が曖昧 | **自作ASD（§7.2）** |
| 🟠 **MeCab + ipadic** | 複雑 | ライセンス条件の解釈が難しい | **BudouX（Apache-2.0）/ SudachiPy（Apache-2.0）** |

**CIで機械的に検証する**（§10.3）:
```bash
# ffmpeg に GPL コンポーネントが混入していないことを assert
ffmpeg -hide_banner -buildconf | grep -q -- '--enable-gpl' && exit 1
ffmpeg -hide_banner -encoders | grep -q 'libx264' && exit 1
# 依存ツリーに AGPL/GPL が無いことを assert
pip-licenses --fail-on="GPL;AGPL;LGPL-3.0"
```

### 13.2 使うライブラリのライセンス（すべてクリーン）

| ライブラリ | ライセンス |
|---|---|
| Electron / faster-whisper / CTranslate2 / whisper.cpp / pywhispercpp / Silero VAD | MIT ✅ |
| MediaPipe / SudachiPy / **BudouX** | Apache-2.0 ✅ |
| PySceneDetect / pyworld / librosa | BSD-3 / 修正BSD / ISC ✅ |
| Whisper / Qwen3 のモデル重み | MIT / Apache-2.0 ✅ |
| Zen Kaku Gothic New / Noto Sans JP / Dela Gothic One / Zen Old Mincho | **SIL OFL 1.1** ✅ |
| ffmpeg（LGPLビルド・x264/x265なし） | LGPL-2.1+ ✅ |

**ffmpeg の推奨ビルド構成**:
```
--disable-gpl --disable-nonfree --enable-shared
--enable-videotoolbox       # Mac（H.264 / HEVC / ProRes）
--enable-nvenc              # Windows
--enable-libopenh264        # フォールバック
--disable-libx264 --disable-libx265
```
さらに **ffmpeg を別実行ファイルとして同梱し `child_process` で起動**すれば、リンクしていないので最も安全です。

> 🟢 **今回の設計では VideoToolbox / NVENC を使うので libx264 は不要**です。M2 Air ではソフトウェアエンコードは熱的にも避けるべき（§8.2）なので、**ライセンスと性能の要求が一致しています。**

### 13.3 🔴 H.264 の特許（ライセンスとは別問題）

FFmpeg のライセンスとは**完全に別に**、H.264/H.265 には **MPEG LA / Access Advance の特許プールへのロイヤリティ義務**が発生しうります。

- **個人利用・無償配布**: 実務上、問題になった例はほぼありません
- **有償販売・年間一定本数超の配布**: 要確認。無償枠の規定はあります
- 回避策: AV1 / VP9（特許フリー寄り）。ただしSNS互換性が落ちるので現実的でない

**→ 収益化のフェーズに入る前（§13.6 の③の直前）に一度確認する**、という位置づけにします。個人開発の初期段階で止まる必要はありません。

### 13.4 SIL OFL の遵守事項（必ず実施）

1. **ライセンス全文を `licenses/` に同梱**し、アプリ内の「ライセンス表記」画面から参照できるようにする
2. **フォントを改変して同じ名前で配布しない**（Reserved Font Name）
3. フォント単体を有償販売しない（アプリに同梱して販売するのは可）

### 13.5 Windows の配布と署名

| 配布形態 | 必要なもの | コスト | 挙動 |
|---|---|---|---|
| **未署名の .exe / インストーラを直接配布** | なし | **無料** | ⚠️ **SmartScreen「WindowsによってPCが保護されました」警告**が出る。「詳細情報 → 実行」で回避可能 |
| **OV コードサイニング証明書** | 証明書購入 | **年1.5〜3万円** | 初期は警告が出るが、DL実績が貯まると消える（評価ベース） |
| **EV コードサイニング証明書** | 証明書 + HWトークン | 年5〜10万円 | **即座にSmartScreen通過** |
| **Microsoft Store 経由** | 開発者登録（**1回 約2,000円**） | 約2,000円（1回） | **署名不要**（Storeが署名）。審査あり |

> **個人開発ソフトの現実**: BOOTH / Gumroad / 自サイトでの直接配布なら、**未署名でも成立します**。SmartScreen警告は個人開発ソフトでは一般的で、インストール手順を丁寧に案内すれば購入者は回避できます。**まずは未署名で始め、売上が立ったら OV 証明書（年1.5〜3万円）を検討**するのが合理的です。

### 13.6 🔴【確定】収益化は Windows 版から — 段階案

**Mac の署名・公証には Apple Developer Program 年99ドル（約1.5万円）が必要**で、未署名の Mac アプリは一般ユーザーには実質配布できません（「壊れているため開けません」と表示され、対処できない）。

一方 **Windows は未署名でも配布でき、Microsoft Store でも1回約2,000円**です。

**段階案**:

```
① 友達に未署名Mac版を渡す（Phase1〜3）
   - コスト: ゼロ
   - Gatekeeper回避は「右クリック→開く」を口頭で伝える
   - 友達1人なら問題なく回避できる（autotelopで実績あり）

② 収益化は Windows 版から始める（Phase4以降）
   - コスト: ゼロ（未署名）〜 2,000円（Microsoft Store）
   - BOOTH / Gumroad / 自サイトで直接配布
   - SmartScreen警告はインストール手順で案内
   - 🔴 Apple Developer Program 年99ドルを当面回避できる
   - 開発機がWindowsなので、サポート対応も自分で再現できる

③ 売れてから Mac 署名に投資（収益が出てから）
   - Apple Developer Program 年99ドル
   - + 必要なら Windows の OV 証明書（年1.5〜3万円）
   - この時点で H.264 特許（§13.3）も確認する
```

**この方針が設計に与える影響**:

| 項目 | 影響 |
|---|---|
| **Windows版の完成度** | 🔴 **Mac版と同等以上に作り込む必要がある**（収益化の主戦場） |
| **Windows のエンコーダ** | NVENC が主力。**GPUがない Windows 環境のフォールバック（OpenH264 / QSV）も用意する**（+1人日、Phase4） |
| **Windows のインストーラ** | NSIS で作る。**SmartScreen警告の案内をインストール手順に含める**（+0.5人日） |
| **開発の優先度** | §10.2 の Windows 先行戦略と**完全に整合**。Windows版を先に完成させることが、Mac非所持対策であり、かつ収益化の準備にもなる |
| **ライセンス** | §13.1 の「最初から避けるものリスト」を厳守。**後から差し替えは不可能**と考える |

> **戦略的な整合**: 「Mac実機が無いのでWindows先行で開発する」（§10.2）と「収益化はWindows版から」（§13.6）は、**同じ方向を向いています**。制約が戦略を規定した良いケースです。

| **モデルの初回DL** | turbo 1.2GB + large-v3 2.3GB + Qwen3 5GB | 初回セットアップUIで明示的に進捗。**必要なものだけDL**（最小構成2.5GB） |
| **SSD容量** | §9.4 の目標 | (a)方式で0.5〜7GB。**解析前に空き容量チェック**・自動削除 |

### 15.3 日本語特有

| 問題 | 対策 |
|---|---|
| 分かち書きがない → 折り返し位置 | **BudouX（§6.6）**。禁則処理は既存 `telop._wrap()` のロジックを併用 |
| 同音異義語の誤変換 | LLM後処理 + hotwords + **操作ログから自動生成される置換辞書**（§12.3） |
| フィラーと意味語の境界 | `context_exceptions` で単独出現時のみ切る。**却下ログから自動学習** |
| 長音・促音の表記ゆれ | 既存 `fillers._norm()` が対応済み |
| 話速（モーラ/秒）の計算 | Whisper出力は漢字混じり。SudachiPy の読み仮名 or 簡易的に文字数/秒 |
| Canvas でのテキスト折り返し | Canvas API に自動折り返しはない。**BudouX（JS版）+ `telop._wrap()` のTS移植** |

### 15.4 アンチパターン

1. **CPUを使う工程を増やす** — M2 Air のファンレスでは直接的な性能劣化（§8.2）
2. **LLMに動画フレームを渡す** — コスト爆発、時刻精度も出ない
3. **LLMに時刻を計算させる** — 必ずずれる。IDで参照させる
4. **LLMに話者切り替えを判断させる** — 非決定的になり、判断材料がテキストで表現できない（§11.4）
5. **LLMに全セグメントの分類を聞く** — M2 Airで8〜16分かかり破綻（§8.7③）
6. **Ultralytics YOLO を使う** — AGPL汚染（§13.1）
7. **x264 を同梱する** — GPL汚染（§13.1）
8. **「商用利用可」だけを見てフォントを同梱する** — 再配布不可のものが多い（§6.7/§13.1）
9. **プレビューをCSS、書き出しをCanvasで別実装する** — 必ずずれる（§6.5）
10. **Phase 0 を飛ばす** — 手戻りが数十人日規模
11. **解析が全部終わるまでUIに何も出さない** — 20分素材で9〜15分の無反応（§8.6）
12. **学習した閾値を自動適用する** — 原因不明の挙動変化。必ず承認ダイアログ（§12.3）
13. **Phase1でIRを①のスキーマだけに絞る** — Phase2/3で全部作り直し（§11.3）
14. **診断情報ボタンを後回しにする** — Mac実機の問題が一切追えない（§10.5）
15. **Mac固有コードを4ファイル以外に書く** — Macで壊れる範囲が予測不能になる（§10.4）
16. **1項目ずつ友達に確認を頼む** — 往復回数が5倍になる（§10.2.2）

### 16.2 判断基準

| 判定 | 条件 | 次にすること |
|---|---|---|
| ✅ **続行** | T1・T5・T6-2・T6-4 がすべて成功条件を満たす | Phase 1 に着手。§14.2 のスケジュールで進める |
| ⚠️ **条件付き続行** | T6-2 or T6-4 が失敗、T1・T5 は成功 | 該当する緩和策を Phase 1 に前倒しし、**工数を+2〜7人日して再スケジュール**してから着手 |
| ⚠️ **設計変更** | **T1 が失敗**（WYSIWYGが成立しない） | 案B（ASS + libass）に変更。**Q2の「後から装飾を追加できる」条件を再確認**してから Phase 1 へ |
| 🔴 **大きな方針変更** | **T5 が失敗**（Mac版がビルドできない） | サイドカーをネイティブ構成に変更（+15人日）。またはMac対応を諦めて**Windows専用アプリにする**（友達は使えないが、収益化は成立する） |
| 🔴 **中止を検討** | T1・T5 の両方が失敗 | 自作アプリを諦め、**CLI + 既存NLE連携**（初版のFCPXML案）に戻す判断もありえる |

> **Phase 0 の最大の価値は「中止/変更の判断ができること」です。** 12人日（週15hで1.5ヶ月）を投資して、169.5人日（同18.5ヶ月）を賭けるかどうかを決められます。

### 16.3 Phase 0 で「やらないこと」

スコープを守るため、以下は Phase 0 では**やりません**:
- レビューUIの作り込み（T1の検証に必要な最小限のCanvas描画のみ）
- タイムラインUI・波形描画
- 話者アクティブ判定の実装（Phase 3。サンプル素材の用意だけ）
- 学習ループ
- インストーラ
