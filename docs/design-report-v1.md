## 1. スコープ設計 — 何を作り、何を作らないか

### 1.1 削るのは「汎用NLE機能」だけ

**①カット ②テロップ ③ズームは全部作ります。** 削る対象は、汎用NLE（Premiere/Resolve相当）が持つ**編集基盤としての一般性**です。

### 1.2 想定タイムライン（この構造に固定する）

```
┌──────────────────────────────────────────────────────┐
│ テロップ層     [T1] [T2]  [T3]      [T4] [T5]        │ ← ②。重なりは上下に自動配置
├──────────────────────────────────────────────────────┤
│ ビデオ         ████████████████████████████████████   │ ← ①。単一素材をカットで分割した区間の連結
│  ＋ズーム        [Z1]         [Z2]                    │ ← ③。ビデオ区間の属性（別トラックではない）
├──────────────────────────────────────────────────────┤
│ BGM            ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░   │ ← 1本のみ。音量とフェードだけ
└──────────────────────────────────────────────────────┘
```

トラック数は可変にしません。**この4層固定**が、実装量を汎用NLEの1/5に抑える鍵です。

## 2. ①②③ の実現可能性

### 2.1 ① カット編集・テンポ調整

| サブ機能 | 実現度 | 手法 | 難所 |
|---|---|---|---|
| 無音カット | ◎ 95% | Silero VAD v6 + ffmpeg `silencedetect` の二重判定 | 閾値が好みに直結 → §12の学習対象 |
| フィラー除去 | ◯ 85% | 既存 `fillers.py`（表記ゆれ正規化済み） | 「まあ」「なんか」は意味を持つ場合がある |
| テンポ調整 | ◯ 80% | 語間ポーズの圧縮（0.5秒超 → 0.15秒） | 間を潰しすぎると笑いどころが死ぬ |
| 言い直し検出 | △ 60〜70% | n-gram重複 + LLM判定 | **最大の難所** |

**言い直し検出の内訳**（正直に）:
- 「これはあの、これはですね」→ 表層n-gram重複で検出可能（易）
- 「今日は3つ紹介します。あ、4つでした」→ 意味的自己訂正。**LLMでないと無理**（中）
- 「〜なんですけど、まあそれは置いといて」→ 切るか残すかは**編集者の好み**（ほぼ不可能）

現実解: 表層重複はルールで確実に取る。意味的訂正はLLMに候補を出させ、**確信度を付けてレビューUIのグレーゾーンに回す**（§3.3）。全自動にしない。

### 2.2 ② 自動文字起こし・テロップ — 精度の現実

2026年2月の日本語自然会話ASRベンチマーク（RTX 5090、20クリップ580秒、[出典](https://neosophie.com/en/blog/20260226-japanese-asr-benchmark)）:

| モデル | WER | CER | RTF | 備考 |
|---|---|---|---|---|
| **qwen3-asr-1.7b** | **0.185** | **0.140** | 0.036 | **最高精度**。句読点も自然。ネットスラング・固有名詞は誤る |
| **whisper-large-v3-turbo** | 0.218 | 0.184 | **0.013** | 文脈理解が最強。弱点は**ハルシネーション** |
| parakeet-tdt-0.6b-v3 | 0.344 | 0.321 | 0.003 | 爆速だが低精度 |
| reazonspeech-nemo-v2 | 0.348 | 0.329 | 0.020 | 放送メディア語彙に強い |
| **kotoba-whisper-v2.0** | 0.534 | 0.495 | 0.008 | **自然会話では実用外**。反復ループ、フィラー直後の語落ち |

**「誤字脱字の修正作業をほぼゼロ」は、単一モデルの精度向上だけでは達成できません。** 忖度せず言います。素の CER 14〜18% は「1テロップ（8〜16文字）につき1〜2回、修正箇所が出る」体感です。

**ただし24GBのおかげで、精度を積み上げる手が全部打てます**（§9.2で詳述）:

| 手 | 効果（CERの相対改善） | メモリコスト |
|---|---|---|
| 1. **2パス構成**（turbo → 低信頼度だけ large-v3 で再認識） | −10〜15% | +4.5GB（両モデル常駐） |
| 2. `hotwords` に固有名詞辞書（**操作ログから自動生成**・§12.3.3） | −8〜15%（固有名詞が多い動画ほど効く） | ほぼゼロ |
| 3. LLM後処理（同音異義語の文脈補正） | −5〜10% | +6GB（Ollama）or API |
| 4. 置換辞書（**同じ誤変換が3回出たら自動登録**） | 使うほど効く | ほぼゼロ |
| **積み上げ後の着地見込み** | **CER 0.184 → 0.11〜0.14** | 合計 約11GB（24GBに収まる） |

> **設計判断**: それでも CER はゼロにならないので、**「修正1箇所あたり30秒 → 3秒」を目標にします**。§3のレビュー速度の考え方をテロップ修正にもそのまま適用します（信頼度でソート、キーボードで「次の要確認へジャンプ→修正→次へ」）。

**スタイル出し分け（通常/補足/強調/怒り）**: 分類タスクなので精度70〜85%。誤分類は「通常」にフォールバックすれば実害が小さい（安全側に倒れる）。ワンクリック変更でき、その操作が学習データになります。

### 2.3 ③ ズーム・画角

| サブ機能 | 実現度 | 手法 |
|---|---|---|
| 人物検出・追跡 | ◎ 90% | MediaPipe Face Detection / FaceLandmarker（Apache-2.0） |
| 9:16 オートリフレーム | ◯ 80% | 顔中心のクロップ枠を時系列平滑化 |
| 「強調箇所で人物アップ」 | ◯ 75% | 韻律z-score + テキスト分類 → ズームキーフレーム |
| **「視聴者が飽きそうな箇所」** | ✗ **不可能** | 下記 |

**不可能な理由**: 本当に推定するには**視聴維持率データ（YouTube Analytics の離脱グラフ）**が要ります。動画単体の信号からは推定できません。LLMに聞けば答えは返りますが、**根拠のないもっともらしい嘘**です。

**代替（③の要件を満たす実装）**: 「飽き」の推定をやめ、**「変化の欠如」という代理指標でUI上に注意マークを出す**。ズームは自動で入れません。

```
if 同一画角が継続 > style.max_static_shot_sec (例 4.5秒):
    → タイムライン上に「⚠ 画が動いていません（4.8秒）」マーカーを表示
    → クリックで「ここにズームを追加」ボタンが出る（適用は人間が決める）
```

**AIが判断を放棄していることが明示される**ので、誤った自動処理より信頼できます。将来 YouTube Analytics の離脱タイムスタンプを取り込めば、この閾値を教師データで最適化できます。

## 3. 【最重要の設計軸】レビュー速度

### 3.1 仮説の評価: **「精度より確認の速さ」は正しい**

```
確認コスト = 「人間が確認する候補数」 × 「1件あたりの確認時間」
```

- 候補が100件、**精度90%（10件が誤り）**とします
- 人間は「どの10件が誤りか」を事前に知りません
- → **精度が何%だろうと、100件全部を確認せざるを得ない**
- 精度を95%に上げても確認件数は100件のまま。**確認コストは1ミリも減りません**

したがって、**「1件あたりの確認時間」を短縮するほうが桁で効きます。**

**ただし重要な補足**: 精度は**間接的には効きます**。精度が上がる＝**確信度の分離が良くなる**ので、「確信度0.90以上は無条件に信じてよい」と言える範囲が広がり、**確認件数そのものが減る**からです。

> **したがって、精度改善の努力は「正解率を上げる」ではなく「確信度のキャリブレーションを良くする（高確信度の候補が本当に正しい状態にする）」に向けるべきです。**

### 3.2 目標値

| | 現状 | 目標 |
|---|---|---|
| 1本あたりのカット作業 | **30〜60分** | **2〜3分**（解析待ちを除く） |
| カット候補の件数（20分素材） | — | 約110〜130件 |
| **人間が実際に見る件数** | 全件 | **25件前後** |
| **1件あたりの判断時間** | — | **2〜2.5秒** |

### 3.3 レビューUI設計案

#### 3.3.1 確信度による3分割（件数を減らす主装置）

| 確信度 | 扱い | 20分素材での想定件数 |
|---|---|---|
| **`conf >= 0.90`** | **デフォルトで承認済み**。レビュー対象外。「高確信度 71件を自動承認しました ▸確認する」で展開可能 | 71件（60%） |
| **`0.60 <= conf < 0.90`** | **レビュー対象**。1件ずつ確認 | **35件（30%）** |
| **`conf < 0.60`** | **デフォルトで却下**（適用しない）。「他に12件 ▸見る」で展開可能 | 12件（10%） |

**+ タイプ別の一括処理**: フィラー除去（「えー」「あの」等）は個別確認不要。**一覧で42件をまとめて表示し、チェックボックスで例外だけ外す**（15秒で完了）。

→ **118件 → 実際に1件ずつ見るのは25件程度**

│              └──────────────────────┘                           │

#### 3.3.3 速度を決める7つの設計

| # | 設計 | 効果 |
|---|---|---|
| 1 | **ループ再生の自動開始** — 候補に移った瞬間に自動再生。**再生ボタンを押させない** | −1.5秒/件 |
| 2 | **🔴 カット適用後の音を聞かせる** — 「切る部分」ではなく「切って繋いだ結果」をループ。人間が判断すべきは「繋ぎが自然か」であって「そこが無音か」ではない | **判断そのものが速くなる。最重要** |
| 3 | **Y/N の2キーで完結し自動で次へ** — マウスを一切使わせない | −1〜2秒/件 |
| 4 | **確信度グループ化**（§3.3.1） | **件数が118→25に** |
| 5 | **🔴 ProRes Proxy の短尺クリップ**（§8.5） — 全フレームIフレーム＋HWデコードで**ループの継ぎ目が瞬時**。H.264だとループ頭でGOP再構築が入り毎回0.1〜0.3秒詰まる | **体感の"サクサク感"を決める** |
| 6 | **境界微調整も同じキーボード** — `←→` で±1フレーム、即座にループ再生が更新される | 微調整1件 15秒→5秒 |
| 7 | **`U` でいつでも1つ戻れる** | 心理的効果が大きい（判断が速くなる） |

#### 3.3.4 【追加提案】「通し確認モード」

候補を1件ずつ見るのではなく、**カット適用後の結果を通しで聞く**モード。

```
カット適用後のタイムライン（14分）を 1.3倍速で再生
  → 違和感があったら [Space] で停止 → 該当カットが自動選択
  → [←→] で境界調整、[N] で却下 → [Space] で再開
```

| | 個別レビュー | 通し確認 |
|---|---|---|
| 20分素材の所要 | 25件×2.5秒 = 1分 + 微調整 = **約2分** | 14分÷1.3 = **10.8分** + 修正 |
| 見落とし | 少ない | 出る |
| 認知負荷 | 高い（連続判断） | 低い（聞くだけ） |

**素材が長いほど個別レビューが有利**。ただし通し確認は「最終確認」としての価値があるので、**両方用意して友達に選ばせる**のが正解です。実装コストは通し確認のほうが小さい。

#### 3.3.5 【追加提案】さらに速くする3案

| 案 | 内容 | 効果 |
|---|---|---|
| **A. 波形の色分け** | 無音を薄赤、フィラーを黄、言い直しを紫で塗る。**明らかなものは再生せずY** | −0.5秒/件 |
| **B. 段階的な閾値** | 初回は「0.8秒以上の無音」だけ提案（確実に切ってよいもの）。承認率95%超なら次回0.6秒に下げる。**AIが徐々に踏み込む** | 初期の信頼獲得。学習ループと直結 |
| **C. 「ながら確認」モード** | 音声だけを繋ぎ、カット位置に「ピッ」を入れて再生。**映像を見ず耳だけで確認** | 通し確認をさらに1.5倍速化 |

#### 3.3.6 所要時間の見積もり（20分素材・候補118件）

| 方式 | 見る件数 | 1件あたり | 合計 |
|---|---|---|---|
| 全件を個別レビュー（素朴な実装） | 118 | 5秒 | **9.8分** |
| 確信度グループ化 + キーボードレビュー | 35 | 2.5秒 | 1.5分 + 微調整8件×5秒 = **2.2分** |
| **上記 + フィラー一括 + ProRes即応** | **25** | **2.2秒** | **0.9分 + 微調整 = 約1.9分** |
| 通し確認モード | — | — | 10.8分 + 修正5件×10秒 = **11.6分** |

| 自動ループ再生 | カット適用後の音 | **該当箇所の音声＋テロップ表示のプレビュー** | **ズーム適用後の映像** |

### 4.2 Tauri を不採用にする理由

1. **🔴 Mac が WKWebView（WebKit）になる**。開発機はWindows（=Chromium系のWebView2）なので、**開発中に一切問題が出ず、友達のMacでだけ壊れる**。**開発者はMacを持っていないので再現すらできません**（§10の制約と最悪の相性）
2. **Canvas の既知の不具合**が複数報告されています。テロップのWYSIWYGレンダリング（§6）は Canvas に全面依存するので直撃します
3. **WebCodecs が WebKit で使えない**。将来の高速化の道が閉ざされます

**「サイズが4倍でも、Macで確実に動くほうがいい」** という判断です。

### 4.3 PySide6 という「リスク半減」の代替案（正直に併記）

| | Electron + Pythonサイドカー | PySide6 単独 |
|---|---|---|
| 言語 | TypeScript + Python | **Python のみ** |
| autotelop 資産の流用 | ◯ サイドカー内で | ◎ **そのまま** |
| プロセス間通信 | 必要（stdio JSON-RPC） | **不要** |

| テロップWYSIWYG | ◎ Canvas の表現力 | ◯ QPainter で同等は可能だが記述量が3倍 |
| **レビューUIの作りやすさ** | ◎ キーボード処理・アニメーション・レイアウトが楽 | △ |
| Mac描画差のリスク | ◎ Chromium統一でゼロ | ◯ Qtも自前描画なので小さい |
| ライセンス | ✅ MIT | ⚠️ LGPL-3.0（PyInstallerで固めると条件充足が判断困難） |
| **推定工数（Phase1）** | 59.5人日 | **47.5人日（−12人日）** |

**Electron を推す理由**: ①テロップWYSIWYG（核心的難所）が Canvas だと圧倒的に楽、②**§3のレビューUIは応答性と細かい演出が命**でWebのほうが作りやすい、③LGPLリスクがない。

**ただし** — 「とにかく完成させることを最優先」なら **PySide6 は合理的**です。12人日（約1ヶ月分）の差は個人開発では大きい。§16 Q1 で確認します。

## 5. プレビュー再生アーキテクチャ

### 5.1 HTML5 `<video>` の限界

編集後のタイムラインは「元素材の複数区間を連結したもの」です。素直にやると破綻します（[出典](https://web.dev/articles/requestvideoframecallback-rvfc) / [W3C issue](https://github.com/w3c/media-and-entertainment/issues/4)）:

- **フレーム精度のシークは保証されない**。`currentTime` の設定は最寄りのキーフレーム近辺に落ちる
- `requestVideoFrameCallback` で実表示フレーム時刻は取れるが**ベストエフォート**
- 区間境界で `currentTime` をジャンプさせると、**毎回シーク遅延（数十〜数百ms）が入りカクつく**

### 5.2 選択肢と推奨

| 案 | 方式 | フレーム精度 | 実装コスト | 反映の遅さ |
|---|---|---|---|---|
| **A** | **カット済みプロキシを事前生成し、単一 `<video>` で再生** | ◎ | **小（3〜5人日）** | ✗ カット変更のたびに再生成 |
| B | 元素材を1本の `<video>` で再生し、区間境界で `currentTime` ジャンプ | ✗ 境界でカクつく | 中（8〜12人日） | ◎ 即時 |
| C | WebCodecs でフレーム単位デコード → Canvas に自前描画 | ◎ | **特大（25〜40人日）** | ◎ 即時 |

**推奨: 案A を基本とし、編集中は案Bを併用（ハイブリッド）**

1. **プレビュープロキシ**: 540×960 H.264 `-g 15`（GOP短め＝シークが速い、サイズが小さい）
2. **編集中は案Bで即時プレビュー**（境界のカクつきは許容）、**レビュー開始時に案Aでプロキシ再生成**
3. **🔴 §3のレビューUIには専用の短尺クリップを事前生成**（§8.5）。「前0.5秒 →（カット）→ 後0.5秒」の約1.2秒を**ProRes Proxy** で25本作る。ProResは**全フレームIフレーム＋M2のメディアエンジンでHWデコード**なので、ループの継ぎ目が瞬時。生成は10〜20秒

案Cは作りません。単体で1〜2ヶ月かかる規模です。

### 5.3 フレーム精度が本当に必要な箇所

| 場面 | フレーム精度 | 実現方法 |
|---|---|---|
| 通常再生・ループ再生 | ✗ 不要 | `<video>` に任せる |
| **カット点の微調整（コマ送り）** | ✅ **必要** | **静止画で解決**: 対象フレームの前後±10フレームを ffmpeg で PNG に切り出し、コマ送りはPNGの切り替えで行う |
| テロップのタイミング調整 | △ ±1フレームで十分 | 同上 |
| 波形上での位置指定 | ✅ 必要 | 波形は独自描画なのでサンプル単位で正確 |

**「コマ送りをPNGでやる」** のがこの設計の肝です。動画プレイヤーのフレーム精度問題を、UIの都合で回避できます。

## 6. 【最重要の技術的難所】テロップの WYSIWYG

### 6.1 `ffmpeg drawtext` を不採用にする理由

- 縁取り（`borderw`）は**1本のみ**、色も1色。二重縁取り不可
- **グラデーション塗り不可**／影は1つだけ・ぼかし不可／背景ボックスは矩形のみ
- 日本語フォントのフォールバック制御が効かない
- **テキストのエスケープが地獄**（`:` `'` `%` `\` すべて特殊文字。日本語の記号でも事故る）

**→ ②の要件（「太くインパクトのあるフォント・赤」「明朝体・別色」）を満たしつつプレビューと一致させるのは不可能です。**

### 6.2 4つの選択肢

| 案 | 方式 | WYSIWYG一致 | 表現力 | 書き出しコスト | 実装 |
|---|---|---|---|---|---|
| A | ffmpeg `drawtext` | ✗ 不一致 | ✗ 貧弱 | ◎ 軽い | 小 |
| B | **ASS字幕 + libass**（プレビューは JASSUB/libass-wasm） | ◎ 同一エンジン | ◯ 縁取り・影・色は可。**グラデーション不可** | ◎ 軽い | 中 |
| **C** | **Canvas でレンダリング → 透過PNG → ffmpeg `overlay`** | ◎ **同一コード** | ◎ **Canvasの全表現力** | ◯ 中 | 中 |
| D | 全編を自前レンダラで合成（WebCodecs） | ◎ | ◎ | ✗ 重い | 特大 |

### 6.3 推奨: **案C（Canvas → PNG → overlay）**

1. **一致が"努力目標"ではなく"構造的保証"になる**。プレビューで使っているのと**同じCanvasコード**で書き出し用PNGを描くので原理的にずれません
2. **表現力**: グラデーション塗り、二重縁取り、角丸背景、letter-spacing。②の「一律ではなくスタイルを変える」要件に圧倒的に有利
3. **スタイル追加のコストが定義1ブロック**
4. ffmpeg 側は `overlay` 1つで済み、ビルド要件が減る（`drawtext` は libfreetype/libharfbuzz/fontconfig を要求）

**案Bも十分に強い**ので代替案として残します。グラデーションが要らないなら案Bのほうが書き出しは軽く、実装も1〜2人日短縮できます（§16 Q2で確認）。

### 6.4 実装設計（性能が肝・M2 AirではCPU負荷を減らすことが最優先）

素朴に「全フレームをPNG化」すると、20分×30fps = 36,000枚で破綻します。**テロップは大半が静止画**という性質を使います。

**レイアウト変化点でセグメント化**:

```
時刻 →
表示中のテロップ:  {}   {T1}    {T1,T2}   {T2}   {}    {T3}   {}
セグメント:        S0 │  S1   │   S2    │  S3  │ S4 │  S5  │ S6
PNG:              なし  1枚      1枚      1枚   なし   1枚   なし
```

- PNG枚数 ≒ テロップ数 × 1〜2。20分素材で200テロップなら **200〜400枚**
- 1080×1920 の透過PNGは文字部分だけなので圧縮後 50〜300KB → 合計 **20〜100MB**
- **Canvas → PNG の生成時間**: `toBlob('image/png')` が20〜60ms。400枚で **8〜24秒**（書き出し全体に対して無視できる）

**overlay の適用方法 — M2 Air ではここがCPUボトルネック**:

| 方式 | CPU負荷 | ディスク | 判定 |
|---|---|---|---|
| **(a) `overlay` を N段チェーン**（`enable='between(t,a,b)'`） | 段数に比例して増える可能性 | 100MB | **要実測（Phase 0）** |
| (b) PNG群を `concat` demuxer で**アルファ付き中間動画**（QTRLE）にして `overlay` 1回 | 低い | **3〜10GB** ⚠️ | ディスクを食う |
| (c) ProRes 4444（アルファ対応・M2でHWエンコード） | **最低** | **30GB超** ❌ | 巨大すぎて不採用 |
| (d) VP9 alpha (yuva420p/WebM) | 高い（libvpxはソフトウェア） | 200〜800MB | CPU負荷が本末転倒 |

> **🔴 Phase 0 の検証項目に「overlay 200段の実行速度をM2 Airで実測」を入れます。** 実測で問題なければ (a)、遅ければ (b) にフォールバックします。SSD容量が厳しい場合（§9.4）は (a) 一択になるので、**この実測は設計の分岐点です**。

### 6.5 落とし穴

| 落とし穴 | 対策 |
|---|---|
| **フォントが読み込まれる前に描画される** | `document.fonts.ready` を待つ。**Webフォントをアプリに同梱**（システムフォント依存にしない。友達のMacとユーザーのWindowsでフォントが違うとWYSIWYGが崩れる） |
| 🔴 **プレビューをCSS、書き出しをCanvasで別実装する** | **最大の罠**。CSSとCanvasは line-height・letter-spacing・フォントヒンティングで**必ずずれます**。**プレビューもCanvasに統一**（`<video>` の上に `<canvas>` を重ねる） |
| デバイスピクセル比（Retina） | Canvas は常に出力解像度（1080×1920）で描き、CSSで縮小表示 |
| Canvas API に自動折り返しがない | 自前実装（既存 `telop._wrap()` の禁則処理ロジックをTypeScriptに移植、約40行） |
| 絵文字のカラー描画 | Win/Mac で見た目が違う → **同梱フォントの範囲に限定**するか使わない |

### 7.2 推奨: **案①（Python サイドカー）を骨格に、ASR は pywhispercpp を同梱**

**韻律抽出と autotelop 資産のために Python は必須**です（librosa/pyworld の JS 書き直しは +10〜15人日）。

**ただし ASR だけは whisper.cpp を使います。** M2 Air はファンレスで、**CPU実行の faster-whisper はスロットリングを最も強く受ける工程**だからです（§8.2）。幸い `pywhispercpp` という Python バインディングがあるので、**サイドカーの中から whisper.cpp を呼べます**。Python サイドカーの枠組みは維持したまま、ASR のバックエンドだけネイティブにできます。

```python
# asr/__init__.py — ここだけがバックエンドを知る
def make_asr(cfg):
    if cfg.platform == "darwin":  return WhisperCppASR(coreml=True, metal=True)  # M2 Air の本命
    if cfg.device   == "cuda":    return FasterWhisperASR("cuda", "float16")     # 開発機
    return FasterWhisperASR("cpu", "int8")                                        # フォールバック
```

**Phase1 は faster-whisper（CPU）で作り、Phase2 で whisper.cpp に差し替える**のが工数上は現実的です（§14）。差し替えコストは +4〜5人日。

### 7.3 サイドカーの起動方式

**stdio JSON-RPC の常駐プロセス**（1リクエストごとにPython起動、はNG）:

```
Electron ──spawn──► python_sidecar (常駐)
    │  {"id":1,"method":"analyze","params":{"path":"...","stages":["asr","vad","prosody","scene","face"]}}
    │  ◄── {"id":1,"stage":"asr","progress":0.32,"eta_sec":180}
    │  ◄── {"id":1,"stage":"asr","done":true,"path":"...asr.json"}   ← 段階ごとに部分結果
    │  ◄── {"id":1,"result":{"analysis_path":"...analysis.json"}}
```

- **モデルのロードは1回だけ**（large-v3 のロードに10〜25秒。毎回起動は許容できない）
- **結果はファイルパスで返す**
- **🔴 段階ごとに部分結果を返す** — §8.6 の「逐次表示」を可能にする最重要の設計

## 8. 【重点】MacBook Air M2 での性能設計

### 8.1 M2 Air の資源と、それぞれの使い道

| 資源 | 使い道 | ライブラリ経由 |
|---|---|---|
| **メディアエンジン**（H.264/HEVC/**ProRes** の HW エンコード/デコード） | 素材デコード・プロキシ生成・最終書き出し・**ProResレビュークリップ** | **ffmpeg VideoToolbox**（`h264_videotoolbox` / `prores_videotoolbox` / `-hwaccel videotoolbox`） |
| **Neural Engine (ANE)** | **Whisperのエンコーダ** | **whisper.cpp の CoreML バックエンド**（`WHISPER_COREML=1`。CPU比3倍超） |
| **GPU (Metal)** | Whisperのデコーダ、顔検出、ローカルLLM | whisper.cpp の Metal バックエンド / **MediaPipe GPU delegate** / Ollama（Metal対応） |
| **CPU（8コア: 4P+4E）** | 韻律抽出、ffmpegのソフトウェアフィルタ、アプリ本体 | librosa / pyworld / swscale |

> **M2 は M1 無印になかった ProRes のハードウェアエンコード/デコードに対応しています。** これが §8.5 の設計に効きます。

### 8.2 🔴 ファンレスによるサーマルスロットリング

MacBook Air M2 には冷却ファンがありません。持続負荷では:

- 短時間（〜2分）: フルクロック
- 2〜5分: 徐々に低下
- 5分以降: 定常状態（ピーク比 **70〜85%**）
- 15分以上の連続負荷: さらに低下しうる（ピーク比 **60〜75%**）

**工程ごとの感受性が大きく違います:**

| 工程 | 主なハードウェア | スロットリング感受性 | 実効係数 |
|---|---|---|---|
| VideoToolbox デコード/エンコード | **メディアエンジン（専用回路）** | ◎ 極めて低い | **0.95** |
| whisper.cpp（CoreML + Metal） | **ANE + GPU** | ◯ 低い | **0.85** |
| MediaPipe（GPU delegate） | GPU | △ 中 | **0.80** |
| Ollama（Metal） | GPU | △ 中 | **0.78** |
| **faster-whisper（CTranslate2）** | **CPU** | ✗ **高い** | **0.70** |
| **ffmpeg ソフトウェアフィルタ（scale/overlay）** | **CPU** | ✗ **高い** | **0.70** |
| librosa / pyworld | **CPU** | ✗ 高い | 0.70 |

#### 設計方針: **CPUを使う工程を減らす**（これが M2 Air 対策の全て）

| # | 対策 | 効果 |
|---|---|---|
| 1 | **ASR は whisper.cpp + CoreML**（faster-whisper の CPU 実行を避ける） | 熱に強く、かつ1.5〜2倍速い。**最大の効果** |
| 2 | **デコード/エンコードは必ず VideoToolbox**（`-hwaccel videotoolbox`。ソフトウェアデコード禁止） | 書き出しのCPU負荷が激減 |
| 3 | **MediaPipe は GPU delegate（Metal）**を使う | CPU delegate 比で熱・速度とも有利 |
| 4 | **解析用プロキシで顔検出**（360p@3fps）。フル解像度をCPUでスケールしない | 顔検出の前処理CPU負荷が1/16 |
| 5 | **overlay の段数を減らす**（§6.4）。ffmpegフィルタが最後のCPUボトルネック | 書き出しのCPU負荷 |
| 6 | 韻律（librosa/pyworld）は **発話区間のみ処理**（無音を飛ばす） | 処理量が約40%減 |
| 7 | **総処理時間を短くすること自体が最大の緩和策** | スロットリングは時間の関数。速く終われば影響が小さい |

> ⚠️ **「工程を間欠にして冷ます」は逆効果**です。総時間が伸びる分、蓄熱時間も伸びます。**一気に終わらせるほうがよい**。

以下 §8.4 の見積もりは、**すべて上記の実効係数を掛けた「持続負荷での実効値」**です。ベンチマークのバースト値そのままではありません。

### 9.2 24GB を活かす精度設計 — **2パス構成を推奨**

ユーザーの「誤字修正をほぼゼロにしたい」という要件に対して、**24GBだからこそ取れる構成**があります。

```
パス1: whisper.cpp large-v3-turbo で全体を高速に文字起こし（20分素材で2.9〜4.7分）
         ↓
       単語レベルの信頼度（prob）を見て、低信頼度セグメントを抽出
       （conf < 0.6 のセグメント ≒ 全体の15〜25%）
         ↓
パス2: そのセグメントだけ large-v3 で再認識（4〜5分相当の音声 → 1.7〜3.6分）
         ↓
       信頼度の高いほうを採用してマージ
         ↓
パス3: hotwords（固有名詞辞書）+ LLM後処理で文脈補正
```

| 構成 | 20分素材の文字起こし時間 | 実効CER見込み | メモリ |
|---|---|---|---|
| turbo 単独 | 2.9〜4.7分 | 0.184 | 2GB |
| large-v3 単独 | 8.7〜14.3分 | ~0.17 | 4.5GB |
| **2パス（turbo + 低信頼度のみ large-v3）** | **4.6〜8.3分** | **~0.16** | **6.5GB** |
| 2パス + hotwords + LLM後処理 | 5.3〜9.2分 | **0.11〜0.14** | 13GB |

**large-v3 単独と比べて、2パスは約半分の時間で同等以上の精度**になります。**これが24GBの最大の活用先**です。

> **補足**: ベンチマークで最高精度だった **qwen3-asr-1.7b（CER 0.140）** も、24GBなら transformers + MPS で載ります（約6GB）。ただしCT2化されておらずMac最適化が未知数なので、**Phase 0 で実測してから採否を決める**のが適切です。実測でRTF 2x以上出れば、パス2をこれに置き換える価値があります。

1. **§6.4 で (a) overlay チェーン方式が通れば、一時ファイルは1GB以下**。Phase 0 の実測が容量設計も左右します
2. **一時ファイルは書き出し後に自動削除**（設定で保持も可）

5. **精度優先モデル（large-v3, +2.3GB）と Ollama（+5GB）は「必要なときにDL」**（初期インストールを2.4GBに抑える）

## 10. 【独立章】開発機と実行機の乖離をどう埋めるか

### 10.1 制約の直視

- **開発**: Windows 11 + NVIDIA GPU
- **実行**: MacBook Air M2 / 24GB / **ファンレス** / Apple Silicon
- **🔴 開発者は Mac を持っていない**

autotelop でも同じ状況で、README には「Mac非所持のため未検証」の項目が並んでいます（FCP実取り込み、effect uid、メディア再リンク）。**今回はアプリ全体がMacで動くので、影響範囲が桁違いに大きい**です。

**これはプロジェクト最大の遅延要因になると見ています。** 「実装 → 友達に渡す → 報告を待つ → 修正」のサイクルに**1〜3日のリードタイム**が毎回入り、それが数十回繰り返されます。累積で**数週間〜2ヶ月の遅延**になりえます。

### 10.2 対策1: GitHub Actions macOSランナーを「CI」ではなく「実行環境」として使う

autotelop で **.app ビルドの実績**があります（無料の macOS ランナー、arm64）。これを**ビルドだけでなくテストと計測に拡張**します。

| やること | 内容 |
|---|---|
| **スモークテスト** | リポジトリに30秒のサンプル動画を入れ、毎PRで「解析が最後まで完走するか」をチェック |
| **golden file テスト** | `analysis.json` / `project.json` / **書き出しMP4の代表3フレームをPNG化したもの** を golden として保存し、差分を検出。**テロップのWYSIWYGの回帰を自動で捕まえられる** |
| **性能回帰チェック** | 各工程の所要時間を記録し、前回比 ±20% を超えたら失敗させる |
| **Python サイドカーの arm64 ビルド** | PyInstaller onedir を毎リリースでビルドし、成果物を配布 |
| **ffmpeg LGPLビルドの検証** | `ffmpeg -encoders` に `h264_videotoolbox` / `prores_videotoolbox` があり、`libx264` が**ない**ことを assert |

> ⚠️ **ランナーは Apple Silicon ですが、サーバ筐体でファンがあります。** M2 Air のファンレスとは冷却条件が違うので、**絶対値の性能見積もりには使えません**。**回帰検出（前回比）にのみ使う**と割り切ってください。

### 10.3 対策2: プラットフォーム差を1箇所に閉じ込める

| 差異 | 閉じ込め先 |
|---|---|
| ASR バックエンド | `sidecar/asr/__init__.py` の `make_asr()`（§7.2） |
| エンコーダ/デコーダ | `ffmpeg/args.py` の `platform_video_args()` （`h264_videotoolbox` vs `h264_nvenc`） |
| 顔検出 delegate | `sidecar/face/__init__.py`（Metal vs CUDA vs CPU） |
| パス・改行・ファイル権限 | Node/Python の標準APIで統一 |
| **描画** | **Electron を選んだ最大の理由。Chromium統一で差がゼロ**（§4.2） |

**これらのファイル以外に `if platform == "darwin"` を書かない**というルールを最初に決めてください。守れれば、Macで壊れる範囲が予測可能になります。

### 10.4 対策3: 友達を「テスター」として運用サイクルに組み込む

友達はIT知識がないので、**「再現手順を書いて」は求めません**。ログで分かるようにします。

| 施策 | 内容 | 実装 |
|---|---|---|
| **🔴「診断情報を書き出す」ボタン** | ログ + 環境情報（機種/OS/メモリ/空き容量）+ 直近の `project.json` + `perf.json` を zip にしてデスクトップに保存。友達はそれを送るだけ | **Phase1 に必須**（1.5人日） |
| **アプリ自身の自己計測（`perf.json`）** | 各工程の所要時間、メモリピーク、**後半の処理速度低下率（=スロットリングの兆候）**を記録 | Phase1（1人日） |
| **クラッシュ時の自動ログ保存** | 落ちても情報が残る | Phase1（0.5人日） |
| **定期的なビルド提供** | 1〜2週間に1度の頻度でリズムを作る | 運用 |
| **画面共有デバッグ** | 週1回30分、FaceTime/Zoom の画面共有で一緒に触る。**再現手順が言葉にできない問題はこれでしか捕まらない** | 運用 |

`perf.json` は **§8 の見積もりを実測で更新する**役割も果たします。

### 10.5 対策4: Mac実機を入手する（強く推奨）

**正直に言うと、これが一番効きます。**

- **中古の M1 MacBook Air（8GB）が 5〜7万円**程度で入手できます
- 8GB では 24GB 前提の精度設計は再現できませんが、**「動くか」「描画が崩れないか」「UIの応答性はどうか」の検証には十分**です
- 「1〜3日のリードタイムが毎回入る」× 数十回 = **数週間〜2ヶ月の遅延**を回避できます
- **プロジェクト全体（157人日 ≒ 1250時間）に対して、5〜7万円は極めて安い保険**です

コスト感度が高いのは承知していますが、**この1点だけは投資を検討する価値があります**。判断は §16 Q5 で伺います。

### 10.6 対策5: Phase 0 で「Mac実機の最初の1往復」を必ず通す

Phase 0（§14）の検証項目に、**友達のM2 Airでの実測**を入れています。

1. Mac版サイドカーがGitHub Actionsでビルドできる
2. それが友達のM2 Airで起動する（Gatekeeper回避も含めて）
3. **20分素材の文字起こしが §8.4 の見積もり ±30% に収まる**
4. **Canvas → PNG → ffmpeg overlay の結果が、M2 Air上でもWindowsと1ピクセル差以内で一致する**
5. **overlay 200段の実行速度**（§6.4 の分岐点）

**この5点が通れば、以降の開発は「見えない不安」ではなく「既知のリスク」になります。**

## 11. 決定論とLLMの責務分割 + IRスキーマ（①②③すべてを最初から定義）

### 11.1 分割原則

> **「時刻・座標・数値」は決定論。「意味・意図・感情」だけLLM。**
> **LLMには動画も音声も渡さない。IRのテキストと数値メトリクスだけ渡す。**

| 処理 | 対象 | 担当 | 使うもの |
|---|---|---|---|
| 音声抽出・CFR正規化・プロキシ生成 | ①②③ | 決定論 | ffmpeg (VideoToolbox) |
| 発話区間検出(VAD) | ① | 決定論 | Silero VAD v6 |
| 文字起こし・単語タイムスタンプ | ①② | 決定論(ML) | whisper.cpp (CoreML) |
| 無音区間の抽出 | ① | 決定論 | VAD区間の補集合 + `silencedetect` |
| フィラー語検出 | ① | 決定論 | 既存 `fillers.py` |
| 表層的な言い直し検出 | ① | 決定論 | n-gram重複 + 時間近接 |
| 韻律メトリクス（z-score） | ②③ | 決定論 | librosa / pyworld |
| シーンカット検出 | ③ | 決定論 | PySceneDetect |
| 顔検出・トラッキング | ③ | 決定論(ML) | MediaPipe (Metal delegate) |
| **意味的な言い直しの判定** | ① | **LLM** | IRのテキスト |
| **テロップスタイル分類** | ② | **LLM → Phase4でローカル分類器** | IRのテキスト + 韻律z-score |
| **誤字・同音異義語の文脈補正** | ② | **LLM** | IRのテキスト |
| **ズーム強調点の最終選択** | ③ | **LLM（候補は決定論が絞る）** | IRのテキスト + 韻律 |
| テロップ分割（折り返し・禁則） | ② | 決定論 | 既存 `telop._wrap()` |
| クロップ枠の平滑化 | ③ | 決定論 | 1€ filter / Savitzky-Golay |
| カット後タイムラインの再計算 | ①②③ | 決定論 | 既存 `cut.remap_point()` |
| レンダリング | ①②③ | 決定論 | Canvas + ffmpeg |

**「感情認識モデル」は使いません。** 日本語で商用可・高精度な音声感情認識OSSは2026年時点でも実質存在しません（SpeechBrain の IEMOCAP は英語、日本語モデルは演技音声由来で汎化が疑わしい）。代わりに **RMS/F0/話速の話者内z-score という連続量**で扱い、「怒り」ラベルは**テキスト側でLLM/分類器が判定**、z-scoreは補強証拠とします。説明可能・軽量・無料です。

> ⚠️ Praat（parselmouth）はGPLです。pyworld（修正BSD）を使ってください。

### 11.2 二重座標系の明示的分離（バグ防止の要）

**カットとテロップ・ズームの整合バグは、ほぼ全て「どちらの時間軸の値か」の取り違えから生まれます。**

| 接頭辞 | 意味 | 誰が持つ |
|---|---|---|
| `src_*` | **元素材のタイムコード**（カット前・素材ファイル先頭から） | `analysis.json` はこれのみ |
| `tl_*` | **編集後タイムライン座標**（カット適用後・シーケンス先頭から） | `remap_point()` を通した後だけ |

**規則**:
1. 解析パイプライン（`analysis.json`）は **`src_*` しか持たない**
2. `remap_point()` を通した瞬間に `tl_*` に改名する。**同じ変数に上書きしない**
3. **内部計算は秒(float)ではなく整数フレーム数で行う**（丸め誤差の累積を防ぐ。カット数が増えるほど致命的）
4. UI表示は `tl_*`、書き出しコマンド生成は両方を使う

**この規則は①②③すべてに適用**されます。テロップの表示時刻もズームのキーフレーム時刻も、カットの影響を受けるからです。

## 12. "自分風"を学習・再現させる方式

### 12.1 自作アプリ化で何が変わったか

**フィードバックループ方式（案d）の価値が決定的に上がりました。**

| | NLE納品案（旧） | **自作アプリ案** |
|---|---|---|
| フィードバックの回収 | 「編集後プロジェクトを書き出して送ってもらう」— 無理のある運用 | **アプリ内の操作がそのままログになる。友達は何もしなくてよい** |
| 回収できる情報 | 最終結果のみ（何を却下したか"推測"するしかない） | **操作そのもの**（却下か微調整か、どれくらい動かしたか） |
| 特徴量の紐付け | 提案IDが保持されるか不確実 | **確実**。提案オブジェクトに直接ひもづく |
| 遅延 | 数日〜数週間 | **即時** |
| 「迷い」の検出 | 不可能 | 可能（同じ箇所を2回触った＝迷った） |

### 12.2 方式比較

| | 方式 | 実装コスト | 初期データ | 精度 | デバッグしやすさ | ランニングコスト |
|---|---|---|---|---|---|---|
| (a) | 宣言的スタイル定義（CLAUDE.md風・自然言語） | 小（1〜2人日） | 0 | △ 揺れる | ✗ 原因追跡不能 | LLM毎回課金 |
| **(a')** | **機械可読スタイルプロファイル（YAML型付き）** | 中（3〜5人日） | 0 | ◎ 完全再現 | ◎ 値1つで結果が変わる | **ゼロ** |
| (b) | 過去完成動画からのルール自動抽出 | 特大（15〜25人日） | ペア20本以上 | ◯ | △ | ゼロ |
| (c) | Few-shot例示 + LLMにタイムライン直接出力 | 中（5〜8人日） | 例20〜50件 | ◯ 意味は強い、時刻は✗ | △ | LLM毎回課金 |
| **(d)** | **UI操作ログのフィードバックループ** | **中（6〜9人日）** | **0（使いながら貯まる）** | **◎** | **◎ 操作履歴が可読** | **ゼロ** |
| (e) | 事例参照(RAG)／小規模分類器 | 中〜大 | ラベル100〜300件 | ◯ | ◯ | ゼロ |

**(a) CLAUDE.md方式を推さない理由**:
1. **非決定性** — 同じ入力で結果が揺れ、原因を切り分けられない。コード生成でCLAUDE.mdが機能するのはテストという検証器があるからで、動画編集にはない
2. **暗黙知は言語化できない** — 「間を詰める」と書いても 0.35秒なのか 0.68秒なのかは決まらない。"自分風"の実体は言語化されない数値
3. トークンコストが毎回かかる
4. フィードバックが構造化されず、矛盾した指示が堆積する

**(b) を推さない理由**: (d) が同じ価値を、初期データゼロ・実装コスト1/3で提供するため。

### 12.3 推奨: **(a') 機械可読プロファイル + (d) UI操作ログのフィードバックループ**

#### 12.3.1 【検証】まず「カットのテンポ」だけで回るか → **回る**

**カットのテンポは、3機能の中で最も学習しやすい対象です。**

| 理由 | 内容 |
|---|---|
| **パラメータ数が少ない** | `silence_cut_threshold_sec` / `silence_keep_margin_sec` / `fillers.context_exceptions` / `repeat.auto_apply_min_confidence` の**実質4個** |
| **1本あたりのサンプル数が多い** | 20分素材で**カット候補118件**。1本で有意な統計が取れる |
| **教師信号が明確** | 「承認/却下」は二値。テロップのスタイル判定（4クラス）より学習が容易 |
| **特徴量が単純** | `silence_dur`（無音長）1変数でほぼ説明できる |
| **効果が体感しやすい** | 閾値が0.05秒変わるだけで候補数が10〜20件変わる。友達が「学習された」と実感できる |

**最小サンプルの試算**: 却下率20%を検出するのに必要なサンプル数は、二項検定で **30〜50件**。**1本のレビューで118件のログが取れる**ので、**1〜3本で最初の更新提案が出せます。**

→ **Phase1（カットのみ）の時点で学習ループが実際に回り始めます。** 友達は「使うほど自分好みになる」体験を、最初のリリースから得られます。

#### 12.3.3 ログ → パラメータへの還元ルール（統計処理のみ。LLM不要）

#### 12.3.4 更新ポリシー（設計品質を決める4点）

1. **🔴 自動適用しない。必ず「提案 → 承認」ダイアログ**
   ```
   ┌─ 編集の傾向を学習しました ────────────────────────┐
   │ 直近5本で、無音カットの提案 512件のうち 118件を    │
   │ 元に戻していました。                                │
   │                                                     │
   │ 無音カットの閾値: 0.55秒 → 0.68秒 に変更しますか？  │
   │ （変更すると、次回の候補が約2割減ります）           │
   │                          [変更する] [今はしない]    │
   └─────────────────────────────────────────────────────┘
   ```
   自動更新すると、たまたま特殊な1本で挙動が変わり原因不明になります。**変更履歴をプロファイルに残す**（`history[]`）ことで、いつでも巻き戻せます。

2. **最小サンプル数を設ける**（カット30件、テロップのスタイル20件、ズーム15件）

3. **「迷い」を重み付けから除外**: 同じ提案を2回以上トグルした操作は、確信のない操作としてカウントを下げる

4. **A/B検証ができる**（自作アプリの特権）: 更新前後のプロファイルを両方保存し、次の1本で「旧設定/新設定」の提案を並べて比較できるモードを用意

#### 12.3.5 分類器への昇格（Phase4）

`telop.style_change` が200件貯まったら、日本語 sentence-transformers 埋め込み + LogisticRegression で分類器を学習し、LLM を置き換えます。

| | LLM（Qwen3 8B / Claude） | ローカル分類器 |
|---|---|---|
| 精度（4クラス） | 70〜85% | 80%前後（200件の教師データで） |
| 速度（20分素材・M2 Air） | **43〜55秒** | **1秒未満** |
| コスト | ローカル無料 / API 8〜25円/本 | **無料** |
| メモリ | 5.5〜6.5 GB | 0.5 GB |

**→ 友達が使い込むほど、速く・軽く・自分好みになります。** §8の処理時間もさらに短縮されます。

## 13. 【必須】ライセンスの精査

### 13.1 ffmpeg — 配布形態別の可否

FFmpeg 本体は **LGPL 2.1+**。ただし `--enable-gpl` を付けた瞬間に全体が GPL になります（[FFmpeg legal](https://ffmpeg.org/legal.html)）。

| 使うもの | ライセンス | 影響 |
|---|---|---|
| **libx264 / libx265** | **GPL** | 🔴 **同梱するとアプリ全体がGPL** → ソース公開義務。**クローズドで配布するなら絶対に含めない** |
| **VideoToolbox**（`h264_videotoolbox` / `prores_videotoolbox`） | **LGPL互換** ✅ | クローズド商用可。**M2 Air の主力** |
| **NVENC**（`h264_nvenc`） | **LGPL互換** ✅ | クローズド商用可。開発機（Windows）用 |
| **OpenH264**（`libopenh264`） | **LGPL互換** ✅ | HWエンコーダがない環境のフォールバック |
| libfdk-aac | nonfree | 🔴 使わない。標準の `aac` エンコーダで十分 |

**推奨ビルド構成**:
```
--disable-gpl --disable-nonfree --enable-shared
--enable-videotoolbox       # Mac（H.264 / HEVC / ProRes）
--enable-nvenc              # Windows
--enable-libopenh264        # フォールバック
--disable-libx264 --disable-libx265
```

**さらに: ffmpeg を「別実行ファイルとして同梱し `child_process` で起動」する構成**なら、そもそもリンクしていないので最も安全です。**この構成を推奨します。**

> 🟢 **今回の設計では、そもそも VideoToolbox / NVENC を使うので libx264 は不要**です。M2 Air ではソフトウェアエンコードは熱的にも避けるべき（§8.2）なので、**ライセンスと性能の要求が一致しています**。

### 13.2 🔴 H.264 の特許（ライセンスとは別問題）

FFmpeg のライセンスとは**完全に別に**、H.264/H.265 には **MPEG LA / Access Advance の特許プールへのロイヤリティ義務**が発生しうります。「FFmpeg が LGPL だから自由」ではありません。

- **個人利用・無償配布**: 実務上、問題になった例はほぼありません
- **有償販売・年間一定本数超の配布**: 要確認。無償枠の規定はありますが、**収益化するなら一度確認すべき**です
- 回避策: AV1 / VP9 で書き出す（特許フリー寄り）。ただしSNS互換性が落ちるので現実的でない

**→ §16 Q5 で「将来の収益化の形」を確認します。**

### 13.4 🔴 フォント — 「商用利用可」と「アプリ同梱可」は別物

**ここが一番事故りやすいです。** 多くの日本語フリーフォントは「作った成果物の商用利用はOK」でも「**フォントファイルをアプリに同梱して再配布するのはNG**」です。

| フォント | ライセンス | アプリ同梱・再配布 |
|---|---|---|
| **Noto Sans JP / Noto Serif JP** | **SIL OFL 1.1**（または Apache-2.0） | ✅ **可** |
| **源ノ角ゴシック（Source Han Sans）** | **SIL OFL 1.1** | ✅ 可（Noto Sans JP と実質同一） |

### 15.2 技術的な落とし穴

| リスク | 内容 | 対策 |
|---|---|---|
| **VFR（可変フレームレート）** | スマホ撮影動画はVFRが多く、カットで累積的に音ズレ | **読み込み時にCFR正規化を必ず入れる**（Phase1）。妥協すると全ての時刻計算が信用できなくなる |
| **フレーム丸めの累積ドリフト** | 秒(float)で計算すると、カット数に比例してずれる | **内部は整数フレーム。offsetは「スナップ済みdurationの累積和」から導出**（§11.2） |

| **単語タイムスタンプのブレ** | ±100〜300ms。そのままカット点にすると語頭/語尾が切れる | VAD境界スナップ + `silence_keep_margin_sec` |
| **Whisperのハルシネーション** | 無音・BGM区間で「ご視聴ありがとうございました」等を生成 | VADフィルタ + `min_confidence`（既存 `telop.py` が対応済み）+ 「無音区間に重なるセグメントは破棄」 |

| **サイドカーのゾンビ化** | Electron が落ちた時にPythonが残る | 親プロセス監視 + `process.on('exit')` でkill。**Windowsは特に残りやすい** |
| **モデルの初回ダウンロード** | turbo 1.2GB + large-v3 2.3GB + Qwen3 5GB | 初回セットアップUIで明示的に進捗。**必要なものだけDL**（最小構成2.4GB） |
| **SSD容量不足** | 40分素材 + 中間動画方式で最大16GB | **解析前に空き容量チェック**。一時ファイル自動削除。キャッシュ管理UI（§9.4） |

### 15.3 縦動画（9:16）

| リスク | 対策 |
|---|---|
| **横→縦で元の横幅の約68%を捨てる**（残るのは31.6%） | 顔中心追従 + 顔が枠外に出そうならスケールを自動で下げる |
| クロップ枠のジッター | 1€ filter / Savitzky-Golay + `face_deadzone_px` + `pan_max_px_per_sec` |
| シーンカットをまたいで枠が滑らかに動く | PySceneDetect のカット点でクロップ枠を**リセット**（連続補間しない） |
| 元素材にテロップやワイプが焼き込まれている | 読み込み時に警告するしかない |
| **そもそも縦で撮影しているなら不要** | §16 Q3 で確認。該当すればクロップ処理を省け、Phase3が約5人日軽くなる |

### 15.4 日本語特有

| 問題 | 対策 |
|---|---|
| 分かち書きがない → 折り返し位置 | 既存 `telop._wrap()` の文字数ベース + 簡易禁則。高度化するなら **SudachiPy（Apache-2.0）**。MeCab+ipadic はライセンスが複雑 |
| 同音異義語の誤変換 | LLM後処理 + hotwords + **操作ログから自動生成される置換辞書**（§12.3.3） |
| フィラーと意味語の境界 | `context_exceptions` で単独出現時のみ切る。**却下ログから自動学習** |
| 長音・促音の表記ゆれ | 既存 `fillers._norm()` が対応済み |
| 話速（モーラ/秒）の計算 | Whisper出力は漢字混じり。SudachiPy の読み仮名 or 簡易的に文字数/秒 |
| Canvas でのテキスト折り返し | Canvas API に自動折り返しはない。`telop._wrap()` を TypeScript に移植（約40行） |

### 15.5 アンチパターン

1. **CPUを使う工程を増やす** — M2 Air のファンレスでは直接的な性能劣化になる（§8.2）
2. **LLMに動画フレームを渡す** — コスト爆発、時刻精度も出ない
3. **LLMに時刻を計算させる** — 必ずずれる。IDで参照させる
4. **LLMに全セグメントの分類を聞く** — M2 Airで8〜16分かかり破綻（§8.7③）
5. **Ultralytics YOLO を使う** — AGPL汚染（§13.3）
6. **x264 を同梱する** — GPL汚染（§13.1）
7. **「商用利用可」だけを見てフォントを同梱する** — 再配布不可のものが多い（§13.4）
8. **プレビューをCSS、書き出しをCanvasで別実装する** — 必ずずれる（§6.5）
9. **Tauri を選ぶ** — Macでだけ壊れ、開発者は再現すらできない（§4.2 + §10）
10. **Phase 0 を飛ばす** — 手戻りが数十人日規模になる
11. **解析が全部終わるまでUIに何も出さない** — 20分素材で8.5〜13.1分の無反応（§8.6）
12. **学習した閾値を自動適用する** — 原因不明の挙動変化。必ず承認ダイアログ（§12.3.4）
13. **Phase1でIRを①のスキーマだけに絞る** — Phase2/3で全部作り直しになる（§11.3）
14. **診断情報ボタンを後回しにする** — Mac実機の問題が一切追えなくなる（§10.4）

## 16. ユーザーに確認すべき質問（5個）

### Q1. UI基盤は Electron と PySide6 のどちらにしますか？
- **Electron**: UI品質◎、テロップWYSIWYG◎、**§3のレビューUIが作りやすい**、**Chromium統一でMac描画差がゼロ**（§10の制約下では大きい）、ライセンス◎。ただし2言語＋二重ビルドで Phase1 が **61人日**
- **PySide6**: Python 1言語で完結、autotelop 資産100%流用、Phase1 が **49人日（−12人日 ≒ 1ヶ月分）**。ただしUIが業務アプリの見た目になりがちで、LGPL の扱いに注意が要る
→ 「友達に使ってもらう消費者向けアプリとしての見た目」と「§3のレビューUIの作り込みやすさ」をどの程度重視するかで決まります。

### Q2. 友達のテロップの見た目に、**グラデーション・二重縁取り・角丸背景・絵文字**は必要ですか？
参考として、友達が今使っているテロップのスクリーンショットか、参考にしている動画を教えてください。「太くインパクトのあるフォント」の具体名が分かればなお良いです。
→ **必要なら案C（Canvas→PNG→overlay）で確定**。**不要（単色＋1本縁取り＋影で足りる）なら案B（ASS/libass）**が選べ、書き出しが軽く、実装も1〜2人日短縮できます（§6.3）。また **SIL OFL の中で近いフォントを選定**できます（§13.4）。

### Q3. 友達の素材は、**撮影時点で既に縦（9:16）**ですか、**横（16:9）で撮って縦に切る**のですか？ 映るのは一人ですか、複数人ですか？
→ **縦撮影なら 9:16 クロップ処理が不要**になり、Phase3 が約5人日軽くなります（ズーム提案は引き続き必要なので③自体は残ります）。**複数人なら話者アクティブ判定**が必要で、ライセンスがクリーンな実装（MediaPipe の口唇ランドマーク + 音声エネルギーの相関）を自作することになります（+5〜8人日）。

### Q4. 友達のMacの**SSD容量と空き容量**を教えてください
` > このMacについて > 詳細情報 > ストレージ` で確認できます。
→ **初期インストールで最大10GB、40分素材の一時ファイルで最大16GB**（中間動画方式の場合）消費します（§9.4）。空きが50GB未満なら、①テロップ透過中間動画を使わない方式（§6.4(a)）を必須にする、②一時ファイルの自動削除をデフォルトON、③精度優先モデル（+2.3GB）とOllama（+5GB）を「必要なときにDL」にする、といった設計判断が必要です。

### Q5. 2つ、判断をお願いします
**(a) Mac実機（中古M1 Air 5〜7万円程度）を入手しますか？**
→ §10.5 の通り、**遅延の回避効果は10〜20人日相当**（週15時間なら1〜1.7ヶ月）です。プロジェクト全体1300時間に対して極めて費用対効果が高い投資です。難しければ §10.2〜10.4 の運用でカバーします。

**(b) 将来の「公開・収益化」は、どの形を想定していますか？** (a) 友達1人に渡すだけ／(b) 無償で一般公開／(c) 有償販売・サブスク
→ 判断が変わる点が3つあります:
1. **Mac の署名・公証**: (a)なら未署名で回避可能（無料）。**(b)(c)なら Apple Developer Program 年99ドルが事実上必須**
2. **H.264 の特許ロイヤリティ**: (a)(b)なら実務上ほぼ問題なし。**(c)なら要確認**（§13.2）
3. **AGPL / GPL の混入**: (a)なら実害は薄いですが、**(b)(c)では致命的**。Ultralytics YOLO と x264 は最初から使わない方針で進めます
