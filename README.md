# ai-video-editor（仮称）

ショート動画向けの AI 動画編集アプリ。素材を読み込むと、カット・テロップ・ズームの編集案を自動生成し、
人間が承認/却下/微調整して書き出す「下ごしらえ自動化」型のスタンドアロンアプリ。

- 開発: touei（Windows 11 + NVIDIA GPU、**Mac 非所持・入手不可**）
- 実利用者: 友達（IT 知識なし、**MacBook Air M2 / 24GB**）
- 最大のペイン: **カット作業に 1 本あたり 30〜60 分** → これを約 2 分にするのが第一目標

## 確定した要件・設計判断

### 機能スコープ

- **① カット**: 無音・フィラー・言い直しの自動カット候補生成 + 高速レビュー UI
- **② テロップ**: 自動文字起こし + 内容/感情によるスタイル自動出し分け（通常=ゴシック白 / 補足=明朝別色 / 強調=太字赤）
- **③ ズーム・画角**: 話者追従の自動クロップ、強調箇所での寄り、単調区間の検知

**3 機能すべて必達。** 削るのは汎用 NLE 機能のみ（マルチトラック、トランジション、カラグレ、
エフェクト機構、キーフレーム UI、部分速度変更、クリップ並べ替え等）。

判断基準:
> 「この機能は、①②③のいずれかの提案を人間が評価・修正するために必要か？」が No なら作らない。

### 技術選定

| 領域 | 決定 | 理由 |
|---|---|---|
| アプリ基盤 | **Electron + Python サイドカー + ffmpeg** | Tauri は Mac が WKWebView になり canvas/video の実装差が実害。Mac 非所持で再現もできない |
| テロップ描画 | **Canvas → 透過 PNG → ffmpeg overlay** | プレビューと書き出しが同一コードを通るので一致が構造的に保証される。後から表現を拡張できる |
| ASR | faster-whisper（Win）/ pywhispercpp + CoreML（Mac） | Mac は CPU を使わない構成にする（ファンレス対策） |
| 精度設計 | **2 パス構成**（turbo で全体 → 低信頼度のみ large-v3 で再認識） | 24GB を活かす。large-v3 単独の半分の時間で同等以上 |
| スタイル学習 | **機械可読 YAML（`style_profile.yaml`）+ UI 操作ログのフィードバックループ** | CLAUDE.md 方式は非決定的でデバッグ不能・数値を表現できないため不採用 |
| エンコード | NVENC（Win）/ VideoToolbox（Mac） | **x264 / x265 は使わない**（GPL 汚染。収益化時に致命的） |
| 物体検出 | MediaPipe 等 | **Ultralytics YOLO は使わない**（AGPL） |
| フォント | Zen Kaku Gothic New Black（通常）/ Dela Gothic One（強調・怒り）/ Zen Old Mincho（補足）/ Noto Sans JP（フォールバック） | すべて SIL OFL 1.1。商用可・アプリ同梱可 |
| 文節改行 | **BudouX**（Google 製・約 20KB・Apache-2.0） | JS 版があるので Canvas 側でそのまま使える。プレビューと書き出しで改行位置が一致することが構造的に保証される |

### 最重要の設計軸: レビュー速度

「AI の精度を上げる」より「人間が秒速で承認/却下できる」ほうが総作業時間に効く。
精度が何 % でも、どれが誤りか事前に分からない以上、人間は全候補を確認せざるを得ないため。

→ **精度改善は「正解率を上げる」ではなく「確信度のキャリブレーションを良くする」に向ける。**

目標値（20 分素材）:

- カット候補 約 118 件 → **人間が実際に見るのは 25 件前後**
  - `conf >= 0.90`（71 件）: デフォルト承認済み
  - `0.60 <= conf < 0.90`（35 件）: レビュー対象
  - `conf < 0.60`（12 件）: デフォルト却下
  - フィラー除去（42 件）: 一覧で一括処理
- **1 件あたり 2〜2.5 秒** / カット作業全体で **約 2 分**

レビュー UI で最も効く設計:
> **「切る部分」ではなく「切って繋いだ結果」をループ再生する。**
> 人間が判断すべきは「そこが無音か」ではなく「繋ぎが自然か」。

#### 🔴 ここで判明した設計上の制約（重要）

1. **CTranslate2 の推論を Python のワーカースレッドで走らせるとデッドロックする。**
   メインスレッドなら 2.7 秒で終わる処理が無限に固まった（Windows）。
2. 別プロセスに逃がしても、**その子プロセスをワーカースレッドから管理すると同じく固まる。**
3. `multiprocessing` の spawn は子で main モジュールを再 import するため、
   `python -m sidecar` 起動だと相対 import に失敗して子が**無言で死ぬ**（stderr にも何も出ない）。

→ **スレッド構成を反転**（メインスレッド = ジョブ実行、別スレッド = stdin 読み取り）し、
   重い処理は**自分自身を `--worker` で起動した subprocess** で実行する。
   PyInstaller で固めた後も同じ経路になるので、配布時だけ壊れることがない。

これは回避策ではなく設計として優れている。プロセスを終了させれば**本当にキャンセルでき**、
推論ライブラリがクラッシュしても RPC ループが生き残る。

### Windows と macOS の描画差（2026-08-18・CI 実測）

「Canvas と ffmpeg が一致する」ことと「**Windows と Mac で同じ見た目になる**」ことは別問題。
開発者が Windows でスタイルを作り、友達の Mac で書き出す構図なので、後者も確認した。

| ケース | 外接矩形 Windows | 外接矩形 macOS | 輪郭の差 |
|---|---|---|---|
| normal | 656 × 230 px | 655 × 230 px | 0.378% |
| note | 943 × 94 px | **943 × 94 px** | 0.485% |
| emphasis | 565 × 140 px | **565 × 140 px** | 0.171% |

**フォントメトリクスは一致する。** 文字サイズ・配置・改行位置が同じなので、
Windows で見た目を作れば Mac でも同じレイアウトになる。
違うのは輪郭のアンチエイリアスだけで、OS のラスタライザの差なので必ず出るもの。
動画では知覚できず、最終書き出しは友達の Mac で行うので実害はない。

CI の `t1-cross-platform` ジョブが**メトリクスの一致だけを守り、アンチエイリアス差は許す**。
Mac を持っていない以上、「Mac だけレイアウトが崩れた」に気づく手段はこれしかない。
